## 2. 브라우저, DOM, 그리고 CSS의 변화

### 1) 브라우저의 본질과 DOM
* 브라우저는 단순 모니터가 아니다: 자바스크립트 소스 코드가 실제로 실행되는 컴파일러/실행 환경이다.
* DOM (Document Object Model): 마우스 클릭이나 호버 같은 이벤트를 브라우저가 인지하고, 특정 엘리먼트를 찾아서 제어하는 구조.
* `<a>` vs `<button>` 태그 구분:
  * `<a>`: 단순 페이지 이동(링크).
  * `<button>`: 자바스크립트 동작(동적 액션). 태그 하나 고르는 것도 다 이유가 있어야 함!

### 2) 성능 최적화 & 네트워크
* 스크립트 파일이나 이미지가 많아지면 웹이 엄청 무거워진다.
* 우리나라 인프라(5G, 광인터넷)만 믿지 말고, 인터넷이 느린 해외나 저사양 기기에서도 잘 돌아가게 데이터 양을 줄이는 습관을 가져야 함.
* 단순 마우스 호버 효과 같은 건 자바스크립트로 처리하지 말고 CSS로 넘겨서 프로그램 부담을 줄여주자.

### 3) CSS 작성 방식의 변화 (Tailwind CSS)
* 전통적 방식: Inline Style -> Internal (`<style>`) -> External (`.css` 파일 분리)
* Tailwind CSS: 레고 블록처럼 미리 만들어진 클래스명(`text-2xl`, `font-medium`, `rounded-md`)을 HTML에 바로 적어서 조립하는 방식.
* React처럼 상태(State) 바뀌는 거에 따라 클래스 뗐다 붙였다 하기 진짜 편함.
* 현업 현실: 요새는 퍼블리셔 따로 없는 회사가 많아서, 백엔드/프론트엔드 구분 없이 퍼블리싱까지 다 할 줄 알아야 시장에서 살아남음.

* NPM & 패키지 매니저:

## 4. CSR vs SSR 및 React / Next.js 비교

### 1) React & CSR (Client-Side Rendering)
* 탄생 배경: 페이스북에서 좋아요, 댓글, 알림 등 실시간 업데이트가 너무 많아지니까 브라우저가 버벅이고 메모리 터지는 거 막으려고 만듦.
* 동작 원리: 
  * 처음에는 빈 껍데기 HTML (`<div id="root"></div>`)만 받음.
  * 그 후 브라우저가 JS 파일을 다 받은 다음에 화면을 직접 채워 넣어 그림.
* 단점:
  1. 초기 로딩 속도 느림: JS 통째로 다운받을 때까지 멍때려야 함.
  2. SEO(검색엔진 최적화) 똥망: 처음에 빈 HTML만 넘어가니까 구글 크롤러가 긁어갈 글자가 없음.
  3. State(상태) 지옥: 컴포넌트 계속 중첩되면 `useState` 전달하느라 Props Drilling 터짐.

### 2) Next.js & SSR (Server-Side Rendering)
* SSR: 서버에서 미리 HTML 다 완성해서 브라우저로 쏴주는 방식. (웹의 원래 근본!)
* Next.js: React의 단점(SEO, 초기 로딩, 상태 지옥)을 보완하기 위해 나온 풀스택 프레임워크/미들웨어.
* App Router (`app/` 디렉토리): 디렉토리(폴더) 만드는 게 곧 페이지 경로(URL)가 됨.
* Next.js를 꼭 써야 하는 이유:
  * 캐싱 (Caching): 서버(미들웨어)에서 미리 데이터를 가져와 메모리에 쟁여둠. 유저 5천만 명이 들어와도 DB 조회를 1번으로 줄여줘서 DB 서버 폭파를 막아줌!
  * 이미지 최적화: 화면에 보이는 것만 먼저 로드(Lazy Loading)하고 알아서 이미지 압축해 줌.

## 5. 서버 통신 & 보안 (Server Actions)

* React + Axios 방식의 위험성:
  * 브라우저(클라이언트)에서 백엔드 API를 직접 호출하면, 개발자 도구 네트워크 탭에 API 주소, 토큰, DB 파라미터가 싹 다 노출됨. 해커들 맛집 됨!
* Next.js Server Actions 방식:
  * 브라우저가 직접 DB/API에 붙는 게 아니라, Next.js 미들웨어 서버가 중간에서 백엔드랑 통신 (Server-to-Server).
  * 브라우저 쪽에는 IP나 통신 구조가 안 보여서 보안이 훨씬 우수함.

## 6. 타입스크립트(TypeScript) & 실무 마인드

* TypeScript 쓰는 이유: 자바스크립트는 변수 타입이 제멋대로 바뀌어서 에러가 자주 남. 백엔드에서 받아오는 데이터 타입을 엄격하게 정해둬야 사고가 안 뜸. (`TSX` 사용)
* 프론트엔드 데이터 가공 금지 원칙:
  * 백엔드에서 받아온 데이터 맘대로 쪼개고 바꾸지 말 것 (데이터 변질 위험).
  * 필요한 형태가 있으면 백엔드 개발자랑 얘기해서 API 설계를 제대로 요청해야 함. 그러려면 백엔드/DB 구조도 어느 정도 알아야 욕 안 먹음!
* React 19 최신 스펙 (`useTransition`):
  * 버튼 여러 번 클릭(연타)하는 거 막으려고 `isPending` 상태를 알아서 잡아주는 기능 등장.
* 로그인 화면 만들 때 생각할 지점:
  * 보안상 "아이디가 틀렸습니다" 보다는 "아이디 또는 비밀번호가 틀렸습니다"가 맞음.
  * 5회 실패 제한 걸 때도 카운트를 어디서 칠 건지 DB/백엔드 로직까지 생각하면서 개발해야 함.
