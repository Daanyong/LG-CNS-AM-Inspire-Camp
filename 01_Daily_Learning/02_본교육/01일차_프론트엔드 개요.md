## 2. 브라우저, DOM, 그리고 CSS의 변화

### 1) 브라우저의 본질과 DOM
* 브라우저는 단순 모니터가 아니다: 자바스크립트 소스 코드가 실제로 실행되는 컴파일러/실행 환경이다.
* DOM (Document Object Model): 마우스 클릭이나 호버 같은 이벤트를 브라우저가 인지하고, 특정 엘리먼트를 찾아서 제어하는 구조.
* `<a>` vs `<button>` 태그 구분:
  * `<a>`: 단순 페이지 이동(링크).
  * `<button>`: 자바스크립트 동작(동적 액션). 태그 하나 고르는 것도 다 이유가 있어야 함!

### 2) 성능 최적화 & 네트워크
* 스크립트 파일이나 이미지가 많아지면 웹이 엄청 무거워진다.
* 우리나라 인프라(5G, 광인터넷)만 믿지 말고, 인터넷이 느린 해외나 저사양 기기에서도 잘 돌아가게 데이터 양을 줄이는 습관을 가져야 함.
* 단순 마우스 호버 효과 같은 건 자바스크립트로 처리하지 말고 CSS로 넘겨서 프로그램 부담을 줄여주자.

### 3) CSS 작성 방식의 변화 (Tailwind CSS)
* 전통적 방식: Inline Style -> Internal (`<style>`) -> External (`.css` 파일 분리)
* Tailwind CSS: 레고 블록처럼 미리 만들어진 클래스명(`text-2xl`, `font-medium`, `rounded-md`)을 HTML에 바로 적어서 조립하는 방식.
* React처럼 상태(State) 바뀌는 거에 따라 클래스 뗐다 붙였다 하기 진짜 편함.
* 현업 현실: 요새는 퍼블리셔 따로 없는 회사가 많아서, 백엔드/프론트엔드 구분 없이 퍼블리싱까지 다 할 줄 알아야 시장에서 살아남음.

## 4. CSR vs SSR 및 React / Next.js 비교

### 1) React & CSR (Client-Side Rendering)
* 탄생 배경: 페이스북에서 좋아요, 댓글, 알림 등 실시간 업데이트가 너무 많아지니까 브라우저가 버벅이고 메모리 터지는 거 막으려고 만듦.
* 동작 원리: 
  * 처음에는 빈 껍데기 HTML (`<div id="root"></div>`)만 받음.
  * 그 후 브라우저가 JS 파일을 다 받은 다음에 화면을 직접 채워 넣어 그림.
* 단점:
  1. 초기 로딩 속도 느림: JS 통째로 다운받을 때까지 멍때려야 함.
  2. SEO(검색엔진 최적화) 똥망: 처음에 빈 HTML만 넘어가니까 구글 크롤러가 긁어갈 글자가 없음.
  3. State(상태) 지옥: 컴포넌트 계속 중첩되면 `useState` 전달하느라 Props Drilling 터짐.

### 2) Next.js & SSR (Server-Side Rendering)
* SSR: 서버에서 미리 HTML 다 완성해서 브라우저로 쏴주는 방식. (웹의 원래 근본!)
* Next.js: React의 단점(SEO, 초기 로딩, 상태 지옥)을 보완하기 위해 나온 풀스택 프레임워크/미들웨어.
* App Router (`app/` 디렉토리): 디렉토리(폴더) 만드는 게 곧 페이지 경로(URL)가 됨.
* Next.js를 꼭 써야 하는 이유:
  * 캐싱 (Caching): 서버(미들웨어)에서 미리 데이터를 가져와 메모리에 쟁여둠. 유저 5천만 명이 들어와도 DB 조회를 1번으로 줄여줘서 DB 서버 폭파를 막아줌!
  * 이미지 최적화: 화면에 보이는 것만 먼저 로드(Lazy Loading)하고 알아서 이미지 압축해 줌.

## 5. 서버 통신 & 보안 (Server Actions)

* React + Axios 방식의 위험성:
  * 브라우저(클라이언트)에서 백엔드 API를 직접 호출하면, 개발자 도구 네트워크 탭에 API 주소, 토큰, DB 파라미터가 싹 다 노출됨. 해커들 맛집 됨!
* Next.js Server Actions 방식:
  * 브라우저가 직접 DB/API에 붙는 게 아니라, Next.js 미들웨어 서버가 중간에서 백엔드랑 통신 (Server-to-Server).
  * 브라우저 쪽에는 IP나 통신 구조가 안 보여서 보안이 훨씬 우수함.

## 6. 타입스크립트(TypeScript) & 실무 마인드

* TypeScript 쓰는 이유: 자바스크립트는 변수 타입이 제멋대로 바뀌어서 에러가 자주 남. 백엔드에서 받아오는 데이터 타입을 엄격하게 정해둬야 사고가 안 뜸. (`TSX` 사용)
* 프론트엔드 데이터 가공 금지 원칙:
  * 백엔드에서 받아온 데이터 맘대로 쪼개고 바꾸지 말 것 (데이터 변질 위험).
  * 필요한 형태가 있으면 백엔드 개발자랑 얘기해서 API 설계를 제대로 요청해야 함. 그러려면 백엔드/DB 구조도 어느 정도 알아야 욕 안 먹음!
* React 19 최신 스펙 (`useTransition`):
  * 버튼 여러 번 클릭(연타)하는 거 막으려고 `isPending` 상태를 알아서 잡아주는 기능 등장.
* 로그인 화면 만들 때 생각할 지점:
  * 보안상 "아이디가 틀렸습니다" 보다는 "아이디 또는 비밀번호가 틀렸습니다"가 맞음.
  * 5회 실패 제한 걸 때도 카운트를 어디서 칠 건지 DB/백엔드 로직까지 생각하면서 개발해야 함.

## 7. 컴포넌트 설계 & 레이아웃 구조 (시멘틱 웹)

### 1) 화면을 소스 코딩으로 쪼개는 연습 (그루핑 & 레이아웃)
* 레이아웃의 지속성: 웹사이트 접속 시 페이지가 이동해도 유지되는 영역(Header, Footer 등)과 계속 바뀌는 본문 영역을 구분해야 한다.
* 아토믹 디자인 패턴 (Atomic Design): 
  * 마이크로 UI 요소(아이콘, 버튼, 입력창 등)를 조합해 큰 컴포넌트를 만들고, 이를 조립해 레고처럼 페이지를 구성하는 방식.
  * 리액트, Next.js, 자바스크립트, PHP 등 모든 웹 기술 생태계에 공통 적용되는 핵심 설계 접근법.
* 뎁스(Depth) 이동 시 렌더링 최적화:
  * 페이지 이동 시 동일하게 유지되는 부분은 재렌더링을 하지 않는 것이 효과적이다.

### 2) React/Next.js의 부모-자식 구조 (Children)
* 부모 컴포넌트(`Body` 또는 `Layout`) 안에 헤더(`Header`), 푸터(`Footer`)를 고정하고, 그 사이에 변경되는 화면(`Children`)만 교체해서 집어넣는 구조.
* 리턴문 규칙: JSX 문법에서는 리턴(return) 시 반드시 하나의 루트 엘리먼트로 묶여서 내보내져야 함.
* 칠드런(Children)을 활용해 부모의 틀은 고정하고 내부 컴포넌트만 가변적으로 갈아 끼우는 형태로 소스 코드와 디자인을 매칭시킴.

## 8. Vercel 배포 & 자동화 (CI/CD)

### 1) Vercel을 통한 빠른 초간단 배포
* Vercel의 역할: Next.js 개발사에서 제공하는 무료/유료 호스팅 및 배포 플랫폼.
* Git 연동 자동 배포: GitHub 저장소(Repository)의 메인 브랜치에 코드 push/PR 취합 시 자동으로 빌드되어 몇 초~분 내로 실제 도메인 주소로 배포됨.
* 개인 포트폴리오 사이트: 취업 및 구직 시 나만의 웹 포트폴리오 배포용으로 Vercel 환경을 적극 활용하자.

### 2) Next.js 프로젝트 생성 및 Git 연동 스텝
* 넥스트 앱 생성: `npx create-next-app@latest .`
* 깃 설정 및 원격 저장소 연결:
  * `git init` -> `git remote add origin <URL>` -> `git push -u origin main`
  * `.gitignore` 설정을 통해 용량이 큰 `node_modules` 폴더는 깃에 올라가지 않도록 예외 처리.
* Vercel 대시보드에서 해당 Git 저장소를 `Import` 한 후 `Deploy` 버튼 클릭만으로 즉시 외부 접속 가능한 URL 생성.

### 3) 터보팩 (Turbopack) & 환경 변수
* 터보팩 (Turbopack): 웹팩(Webpack) 대비 엄청나게 빠른 빌드 속도를 자랑하며, 코드 수정 후 재배포 시 십여 초 만에 업데이트가 반영됨.
* 환경 변수 (Environment Variables): 카카오 소셜 로그인 API 키, DB 접속 정보 등의 보안 정보는 Vercel 환경변수 메뉴에서 안전하게 관리함.

## 9. Git 트러블슈팅 & 커서(Cursor) AI 활용법

### 1) Git 원격 주소 변경 (Troubleshooting)
* 기존 원격 저장소 URL이 잘못되었거나 이미 존재할 때:
  * `git remote set-url origin <새로운 URL>` 명령어를 통해 변경 처리.
* 트러블슈팅 기록: 문제 발생 시 해결 과정을 마크다운(`.md`) 파일로 정리하여 나만의 학습 일지나 기밀 노트로 보관하는 습관을 들이자.

### 2) AI 에이전트(Cursor, ChatGPT 등) 활용 시 주의사항
* 전문 툴 활용: 코드 전체 문맥을 읽을 수 있는 Cursor 에디터 같은 개발 전용 AI 도구를 권장.
* 하지 마라(Constraints) 지침: AI에게 "무엇을 해라"보다 "무엇을 하지 마라"(기존 멀쩡한 구조 건드리지 말 것 등)를 명확히 제약해야 환각(Hallucination) 및 코드 엉킴을 막음.
* 검증 능력의 필요성: AI가 제시한 코드나 해결책이 맞는지 판단할 기본 실력(지식)이 있어야만 AI를 효율적 도구로 제대로 쓸 수 있음.

## 10. 프론트엔드 실무 태도 및 채용 시장 현황

### 1) 채용 시장과 공급/수요
* 시장 상황: 교육생 중 상당수가 백엔드/풀스택을 선호하지만, 상대적으로 프론트엔드를 깊이 있게 다루는 인원의 수가 적어 명확한 전문성을 갖추면 경쟁력이 있음.
* 백엔드 채용의 신중함: 백엔드는 서버 및 DB 운영 책임이 커 채용을 매우 신중하게 하므로, 단순 '백엔드가 많이 뽑히니까'라는 생각만으로 선택하는 것은 위험함.

### 2) 디테일(Detail)과 UX 처리 능력
* 꼼꼼한 예외 처리 예시:
  * 검색창 입력 시 자동으로 X (초기화) 버튼 생성 및 클릭 시 텍스트 삭제 처리.
  * 모바일 환경에서의 탭(Tap) 반응 속도 고려, 중복 클릭(연타) 방지 및 로딩 상태(Spinner) 표시.
  * 로그인 실패 시 "아이디 존재 안 함" 같은 디테일한 정보 대신 보안 통념에 맞춰 메시지 제공.
* 기획서에 기재되어 있지 않아도 유저 경험(UX)과 서비스 안정성을 위해 개발자가 스스로 챙길 수 있는 세심함이 실력차를 만든다.

* 넥스트JS 같은 기술은 리액트, 자바스크립트 등 기본 개념이 먼저 잡혀있어야 독해가 수월하므로 차근차근 구글 번역 등을 활용해 훑어보는 연습 필요

### Q2. 신입 프론트엔드 개발자에게 바라는 점이 있다면?
* 단순히 문법이나 기술을 외워서 쓰는 게 아니라 구조와 원리를 이해하고 있는지 검증함.
* 모르는 것은 솔직히 모른다고 인정하고, 퍼블리싱 기본기와 프론트-백엔드 간 통신 구조를 파악하고 있는 태도가 중요.

### Q3. 백엔드 서버와 Vercel 배포는 별개인가요?
* Vercel은 Next.js(프론트엔드 및 미들웨어) 영역이며, Java Spring이나 외부 백엔드 서버는 AWS EC2, 도커(Docker) 컨테이너 환경에 별도 배포 후 API로 연결함.

### Q4. 성능 측정 툴(Lighthouse 등)의 수치에 연연해야 하나요?
* 수치상의 점수에 과도하게 집착하여 포트폴리오에 "제 코드가 성능 100점이라 최고입니다"라고 과시하는 것은 실무 관점에서 비추천. 웹 표준과 유저 경험 최적화에 중점을 둘 것.

### Q5. Vite vs Next.js vs 상태관리 라이브러리(Redux, Zustand 등)?
* Vite: 서버 없이 라이트한 CSR 리액트 앱이나 데모/스파베이스(Supabase) 연동 프로젝트 구축 시 자주 쓰임.
* Next.js: 서버 사이드 렌더링(SSR), Caching, Server-to-Server 통신을 기본 지원하는 현대 프론트엔드 생태계의 대세. 둘 다 알아두면 좋음.
* 상태 관리: Next.js 환경으로 오면 글로벌 상태 관리(Redux 등)에 대한 고민 패턴이 서버 데이터 중심으로 바뀌므로 상태 관리에 대한 부담을 줄여도 됨.
