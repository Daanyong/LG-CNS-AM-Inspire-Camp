## 1. ArrayList와 제네릭

### 제네릭을 쓰는 이유

- `ArrayList`에 타입을 지정하지 않으면 아무 타입이나 담을 수 있다.
- 꺼낼 때가 문제다. 꺼낸 값은 `Object` 타입이라 `String`으로 쓰려면 하위 타입으로 형변환을 해야 하는데, 다른 타입이 섞여 있으면 오류가 난다.
- 담을 타입을 `String`으로 고정하면 다른 타입을 넣으려 할 때 컴파일 단계에서 에러가 난다. 런타임이 아니라 컴파일 타임에 걸러준다는 게 핵심이다.

```java
ArrayList<String> list = new ArrayList<>();  // 오른쪽 타입은 생략 가능, <>를 다이아몬드 연산자라고 부른다
list.add(10); // 컴파일 에러
```

### 왼쪽 타입을 List로 선언하기

```java
List<String> list = new ArrayList<>();
```

- `List`는 인터페이스, `ArrayList`는 구현체라서 상속 관계다. 부모 타입 변수에 자식 객체를 대입하는 것이 다형성이다.
- `List`로 선언하면 나중에 `LinkedList`로 바꿔도 코드를 덜 고쳐도 돼서 확장성이 좋다.
- 대신 `List` 변수로는 `List`가 가진 메서드만 호출할 수 있고, `ArrayList` 타입으로 선언하면 자체 메서드까지 호출 범위가 더 넓다.

### Vector와 ArrayList

- `Vector`는 초창기 모델로 멀티 스레드에서 안전하지만 느리다.
- `ArrayList`는 멀티 스레드에서 안전하지 않을 수 있어서, 스레드 여러 개가 값을 조작할 때는 동기화 처리가 필요하다.

### 주요 메서드

`add`, `add(index, e)`(특정 위치 삽입), `addAll`, `clear`, `clone`, `contains`, `forEach`(람다, JPA 때 설명 예정), `get`, `remove`, `size`, `toArray`

### 구현한 것 : PersonManager 배열 버전을 ArrayList 버전으로 변경

- 기존에 배열에 `PersonEntity`를 담던 부분을 `List<PersonEntity>`로 바꾸고, 배열 각 칸에 넣던 걸 `add`로 바꿨다.
- 출력, 집계 메서드들은 향상된 for문을 쓰고 있어서 안쪽 로직은 그대로였고 매개변수 타입만 `List`로 바꿔주면 됐다.
- 컬렉션을 쓰면 배열이든 리스트든 같은 방식으로 순회할 수 있어서 수정할 곳이 적다는 걸 확인했다.

## 3. 상속

- `Employee`와 `Manager`가 이름, 급여, 생년월일, `getDetails`가 거의 똑같이 중복되는 문제에서 시작했다. 직군이 늘면 또 복붙해야 하고 속성 하나 추가하려면 전부 고쳐야 한다.
- 공통 부분을 부모로 빼고 상속받게 하는데, 무조건 하는 게 아니라 의미상 is-a 관계가 성립할 때만 쓴다. (Manager is an Employee)
- 문법은 `class Manager extends Employee`. 자식 클래스에는 자기만 가진 속성과 메서드만 적는다.
- 자바는 단일 상속만 가능하다. 다중 상속이면 같은 이름이 부모 둘에 있을 때 누구 것인지 모호해지기 때문이다. 대신 인터페이스는 여러 개 구현할 수 있어서 이걸로 단일 상속의 제약을 보완한다.

## 4. 리팩토링과 디자인 패턴

- 디자인 패턴은 설계 시점에 객체지향적인 패턴을 미리 적용하는 것이고, 리팩토링은 일단 짠 코드에서 안 좋은 부분을 찾아 구조를 개선하는 것이다. 요구사항이 바뀌어서 고치는 게 아니라 재사용성을 높이려고 내부 구조를 바꾸는 것. 목적은 둘 다 더 객체지향적이고 확장성 좋은 코드다.
- 스프링도 디자인 패턴이 많이 녹아 있다고 한다.
- 이클립스와 인텔리제이에는 리팩토링 메뉴가 있어서 일부를 에디터가 해준다.

### 구현한 것 : Extract Superclass로 부모 클래스 추출

- `Manager`와 `Clerk`(평사원)가 이름, 급여 필드와 `getName`, `getSalary`가 중복이었다. 급여 인상 메서드(`manageSalary`)는 내부 구현이 달라서 제외했다.
- Refactor 메뉴의 Extract Superclass로 `Employee`를 추출하고 두 클래스가 상속받게 했다. 올릴 멤버는 필드 2개와 getter 2개.
- 결과를 보니 필드가 `protected`로 올라갔고 `Clerk`에 필드가 그대로 남아 있어서 직접 지워야 했다. 리팩토링 도구가 완벽하지 않다.
- 필드를 `private`으로 바꾸면 자식에서 직접 접근이 안 되므로, 부모에 이름과 급여를 받는 생성자를 만들고 자식 생성자에서 `super(name, salary)`로 초기화하게 했다.
- `Manager`에는 `department` 속성과 getter를 추가했다. 이름, 급여, 부서를 받는 생성자에서는 `this(name, salary)`로 기존 생성자를 호출하고 부서만 따로 초기화했다. 부서는 부모에게 받은 게 아니라 `Manager`만의 속성이다.

## 5. 추상 클래스

- 메서드에 `abstract`를 붙이면 바디 없이 선언만 한다. 바디를 같이 쓰면 에러.
- 추상 메서드가 하나라도 있으면 클래스도 `abstract`여야 한다. 반대로 추상 메서드가 없어도 클래스에 `abstract`는 붙일 수 있다.
- 추상 클래스는 스스로 객체 생성을 못 한다. `new Employee()`는 에러이고 `Employee e = new Manager(...)`는 된다. 추상 메서드는 구현이 없는데 객체를 만들면 호출했을 때 뭐가 실행될지 알 수 없기 때문이다.
- 추상 클래스는 추상 메서드와 구체 메서드를 둘 다 가질 수 있다.
- 추상 메서드를 쓰는 이유는 오버라이딩 강제다. 일반 메서드면 오버라이딩을 해도 되고 안 해도 되지만, 추상 메서드는 자식이 구현 안 하면 컴파일 에러가 난다.
- 오버라이딩은 메서드 선언부가 똑같아야 해서 이름이 다르면 오버라이딩이 아니다. `@Override`를 붙이면 컴파일 타임에 검사해줘서 실수를 막는다.

### 구현한 것

- `Employee`를 `abstract class`로 바꾸고 `abstract manageSalary()`를 선언했다.
- `Manager`와 `Clerk`가 각자 `@Override`로 급여 인상 로직을 구현하게 했다. 하나라도 빼먹으면 에러가 나는 걸 확인했다.

## 6. 다형성

### 변수 타입에 따른 호출 범위

```java
Employee e1 = new Manager("홍길동", 2500000, "인사부");
Manager  e2 = new Manager("홍길동", 2500000, "인사부");
```

- 실제 객체는 둘 다 `Manager`로 같다.
- 하지만 `e1`은 `Employee`가 가진 `getName`, `getSalary`까지만 호출되고, `e2`는 `getDepartment`까지 호출된다.
- 호출 가능한 범위는 왼쪽 변수 타입으로 정해진다. `List` 대 `ArrayList`와 같은 개념이다.
- `Employee` 타입 변수로 `getDepartment`를 쓰려면 `Manager`로 형변환(캐스팅)해야 한다.

### 다형성의 의미

- 다양한 모양으로 변형된다는 뜻. 부모 타입 하나로 여러 하위 객체를 다룰 수 있다.
- 하위 클래스가 많아지면 각각 따로 다루기 피곤해서, 호출하는 쪽에서는 부모 타입 하나로만 보겠다는 취지다. 라디오, TV, MP3를 전부 기기라는 타입 하나로 바라보는 것과 같다.
- 이 개념이 내일부터 할 스프링 의존성 주입 이해에 필요하다고 한다.

### 구현한 것 : 이종 컬렉션

- `Employee` 타입 배열에 `Clerk`와 `Manager`를 섞어서 담고 for문 하나로 돌렸다. 이렇게 여러 종류가 섞인 컬렉션을 이종 컬렉션이라고 부른다.
- 반복문 안에서 이름과 급여를 출력하고 `manageSalary`로 급여를 인상한 뒤 다시 출력했다. 객체마다 오버라이딩된 구현이 실행된다.
- 부서명은 `Manager`에만 있어서 출력 전에 `Manager`로 캐스팅해야 하는데, 배열에 `Clerk`도 있어서 무조건 캐스팅하면 `ClassCastException`이 난다. 그래서 `instanceof`로 실제 객체가 `Manager`인지 먼저 확인한 뒤에 캐스팅했다.

```java
if (emp instanceof Manager) {
    ((Manager) emp).getDepartment();
}
```

### 적용 전후 비교

- 적용 전 : 직군마다 변수를 만들고 똑같은 출력 코드를 반복한다. 직군이 늘면 코드를 계속 추가해야 한다.
- 적용 후 : 직군이 늘어도 배열에 객체를 추가하는 부분만 고치면 되고 for문은 수정 없이 그대로 쓴다.
- 요구사항이 바뀌어도 기존 코드를 최대한 안 고치게 하는 게 객체지향의 가장 큰 목적이다.

## 7. 도서 관리 예제 (다형적 인자)

### 구조

- `Publication`이 최상위 클래스이고 `Magazine`, `Novel`, `ReferenceBook`이 상속한다. 각각 자기만의 속성(발행 주기, 저자와 장르, 분야)을 갖고 공통 속성은 부모 생성자를 `super`로 호출해 초기화한다.
- `Publication`에서 `toString`을 오버라이딩해서 제목을 반환하게 했다. 원래 `Object`의 `toString`은 클래스명과 해시코드가 나온다. `println`에 객체를 넣으면 `toString`이 자동 호출된다.

### 구현한 것

- `Publication[]` 배열에 세 종류 객체를 담고 반복문으로 `toString` 결과를 출력했다.
- 가격 수정 메서드 `modifyPrice(Publication pub)`를 만들었다. 안에서 `instanceof`로 종류를 구분해 할인율(매거진 0.6, 소설 0.8, 참고서 0.9)을 정하고 가격에 곱해서 다시 설정한다. `int`에 `double`을 곱하면 `double`이 되므로 `int`로 다시 캐스팅해야 한다.
- 소설 9,800원이 변경 후 7,840원으로 나오는 걸 확인했다.

### 다형적 인자

- 매개변수를 부모 타입으로 받는 것을 다형적 인자라고 한다.
- 이게 안 되면 `modifyPrice(Magazine)`, `modifyPrice(Novel)`, `modifyPrice(ReferenceBook)`처럼 종류마다 메서드를 만들어야 하고, 책 종류가 늘 때마다 계속 추가해야 한다.
- 부모 타입 하나로 받으면 메서드 하나로 처리되고 확장에 유리하다. 이쪽이 더 객체지향적이다.

## 8. 인터페이스

### 개념

- 전통적인 인터페이스는 모든 메서드가 추상 메서드이고 스스로 객체 생성이 안 된다. 추상 클래스는 구체 메서드도 가질 수 있다는 점이 다르다.
- 메서드는 묵시적으로 `public abstract`, 변수는 묵시적으로 `public static final`이다. `protected` 같은 접근제한자를 쓰면 에러.
- 자바 8부터 `default`, `static` 키워드로 바디를 가질 수 있고, 자바 9부터는 `private` 메서드도 가능하다.
- 클래스는 `extends`로 상속하고 인터페이스는 `implements`로 구현한다. 인터페이스는 여러 개 구현 가능.

### 구현한 것 : Animal 예제

- `Animal` : 추상 클래스. `protected int legs`, 다리 수를 받는 `protected` 생성자, 추상 메서드 `eat()`, 구체 메서드 `walk()`. 기본 생성자는 만들지 않았다.
- `Pet` : 인터페이스. `getName`, `setName`, `play`.
- `Cat` : `Animal`을 상속하고 `Pet`을 구현. 이름을 받는 생성자에서 `super(4)`로 부모 생성자를 호출하고, 기본 생성자에서는 `this("")`로 이름 받는 생성자를 호출한다.
- `Spider` : `Animal`만 상속. 다리 8개라서 `super(8)`.
- `Fish` : `Animal` 상속 + `Pet` 구현. 다리 0개. 부모의 `walk()`와 동작이 달라서 헤엄친다는 내용으로 오버라이딩했다.

### 부모에 기본 생성자가 없을 때

- 생성자는 상속되지 않는다.
- 부모에 기본 생성자가 있으면 컴파일러가 자식 생성자 첫 줄에 `super()`를 자동으로 넣어준다.
- 부모에 기본 생성자가 없으면 이게 불가능해서 "부모에 기본 생성자가 없으니 다른 생성자를 명시적으로 호출하라"는 에러가 난다. 자식 생성자에서 `super(...)`로 직접 호출해야 한다.

### 객체 생성 방식에 따른 호출 범위

`Cat`은 `Animal`이면서 `Pet`이라서 세 가지로 만들 수 있다.

```java
Cat c = new Cat("나비");
Pet p = new Cat("나비");
Animal a = new Cat("나비");
```

| 변수 타입 | 호출 가능한 메서드 |
|---|---|
| Cat | 5개 전부 (getName, setName, play, eat, walk) |
| Pet | getName, setName, play |
| Animal | eat, walk |

같은 객체여도 변수 타입에 따라 호출 범위가 달라진다.

## 9. 스프링 프레임워크 개요

### Maven과 Gradle

- 스프링으로 개발하면 외부 라이브러리가 많아서 빌드 도구를 쓴다. 프론트엔드의 npm과 비슷한 역할이다.
- Maven : 컴파일, 테스트, 패키징(jar, 웹이면 war)을 해주는 빌드 자동화 도구. 라이브러리는 Maven 저장소에서 받는다. npm의 npmjs 같은 거대한 저장소 역할이다.
- `pom.xml` 파일에 의존성을 XML로 적어서 프로젝트와 의존성을 관리한다. npm의 package.json 같은 역할.
- Gradle : Maven과 역할이 같은데 XML 대신 Groovy나 Kotlin 스크립트를 쓰고 더 빠르다. 안드로이드 스튜디오의 표준 빌드 시스템. 저장소는 Maven 저장소를 같이 쓴다.
- 스프링 프레임워크 수업은 Maven으로 진행한다.

### 스프링 모듈

- 코어, 빈, 컨텍스트 : 의존성 주입과 IoC 담당. 이번에 중점으로 볼 부분
- AOP : 관점 지향 프로그래밍
- ORM : 객체와 관계형 DB 연결. SQL을 직접 안 쓰고 객체로 데이터를 다룬다
- 테스트 : 클래스가 잘 동작하는지 테스트
- TX : 트랜잭션 처리. DB 연동 시 데이터 정확성 유지
- 웹 MVC : 웹 공통 처리
- 웹소켓 : 양방향 통신

### 웹 MVC와 웹플럭스

- 동기 방식은 요청을 보내고 응답이 올 때까지 기다렸다가 다음 단계로 넘어간다. 순서가 보장된다.
- 비동기 방식은 요청을 보내놓고 바로 다음 단계로 넘어간다. 응답은 바로 올 수도, 나중에 올 수도 있다.
- 웹플럭스는 5 버전에서 추가된 비동기 방식인데 함수형 프로그래밍 기반이라 어렵다. 웹 단이 비동기면 DB 단도 비동기여야 한다.
- 우리는 동기 방식인 웹 MVC와 ORM을 쓴다.

### 프레임워크와 라이브러리의 차이

- 프레임워크는 비기능 요구사항(성능, 확장성 등)을 만족하는 구조와 기능을 안정적으로 실행하게 만든, 반쯤 완성된 소프트웨어다. 우리가 업무 로직을 붙여서 애플리케이션을 완성한다. 프로젝트마다 반복되는 하부 구조 구현을 줄여준다.
- 핵심 차이는 호출 흐름의 주도권이 누구한테 있냐다.
  - 라이브러리 : 개발자가 `new ArrayList()`로 직접 객체를 만들고 메서드를 호출한다. 주도권이 개발자 코드에 있다.
  - 프레임워크 : 개발자가 DAO나 컨트롤러 클래스를 만들어 두면 프레임워크가 객체를 생성하고 라이프 사이클을 관리하면서 개발자 코드를 호출한다. 주도권이 프레임워크에 있다. JUnit이 테스트 클래스를 알아서 객체로 만들고 `@Test` 메서드를 호출하는 것도 같은 예다.
- 면접에서 이 차이를 물어볼 수 있다고 했다.

### IoC와 DI

- IoC(제어의 역전) : 객체 생성부터 소멸까지의 생명 주기 관리를 개발자가 아니라 스프링 컨테이너가 한다. 컨테이너가 설정 메타데이터를 읽어서 객체를 만들고 관리한다. 제어 흐름이 일반적인 프로그램과 반대라서 역전이라고 부른다.
- 설정 메타데이터는 XML이나 어노테이션으로 작성한다. 스프링 부트는 XML이 없지만 내부 동작을 이해하려면 XML로 먼저 배우는 게 좋아서 스프링 프레임워크부터 한다.
- DI(의존성 주입) : 클래스 A가 클래스 B를 참조할 때, A와 B 객체를 컨테이너가 만들고 A의 변수나 setter 메서드를 통해 B 객체를 넣어주는 것. XML에 A가 B를 참조한다고 적어두면 컨테이너가 읽고 연결해 준다.
- 프레임워크와 라이브러리를 구분하는 기준은 실행 제어가 어디서 일어나느냐다.
