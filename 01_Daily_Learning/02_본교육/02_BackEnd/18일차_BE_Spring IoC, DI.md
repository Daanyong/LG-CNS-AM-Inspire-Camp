## 1. 스프링 프레임워크란

### 스프링 공식 사이트 설명

- 프로그래밍 모델은 프로그램을 짤 때 쓰는 여러 라이브러리 같은 걸 말한다.
- 설정 모델이 따로 필요한 이유는 객체 생성을 우리가 직접 하지 않기 때문이다. 우리가 만든 클래스 이름이 뭔지, 그 클래스가 어떤 클래스에 의존하는지, 스프링이 제공하는 클래스를 가져다 쓸 때도 스프링 빈으로 등록되게 하는 설정이 필요하다. 이런 설정 파일을 설정 모델이라고 한다.
- 스프링의 핵심은 애플리케이션 레벨의 인프라 지원이고 이걸 배관, 즉 플러밍이라고 표현한다. 건물에서 상하수도 같은 설비가 베이스인 것처럼 스프링이 그런 기반 부분을 맡을 테니 개발자는 비즈니스 로직 작성에 집중하라는 말이다.

### 스프링 프로젝트들

- 마이크로미터: 로그 같은 걸 남겨서 모니터링하는 용도. 스프링 부트 버전이 올라가면서 부트 안에 들어왔다.
- 리액터: 비동기 지원 프로젝트. 동기 방식에서는 서버로 톰캣을 쓰는데 비동기 방식에서는 컨테이너로 네티를 쓴다.
- 스프링 부트: 톰캣이 내장돼 있고 XML 설정을 하지 않는다. 사실 부트가 핵심이고 프레임워크가 원조라고 보면 된다. 부트를 제대로 이해하려고 프레임워크를 짧게 보는 중이다.
- 스프링 데이터: DB 연동. JPA, 몽고DB, 레디스, 아파치 카산드라, 카우치베이스, 네오포제이(그래프 데이터) 등. R2DBC는 비동기 반응형 관계형 DB 연동인데 웹단이 비동기면 DB도 비동기로 이어져야 해서 필요하다.
- 스프링 클라우드: 클라우드 설정, 게이트웨이, 쿠버네티스 등. 다음 선생님 파트.
- 스프링 AI: LLM 연동. 이건 나중에 짧게 다룬다고 했다.
- 스프링 시큐리티: 보안

### 정의 키워드

자바 엔터프라이즈 개발을 편하게 해주는 오픈소스 경량급 애플리케이션 프레임워크.

- 애플리케이션 프레임워크: 특정 계층이나 업무에 국한되지 않는, 범용적이고 전체를 아우르는 프레임워크.
- 경량급: 예전에는 EJB 컨테이너까지 있는 WAS가 있어야 J2EE의 여러 라이브러리를 쓸 수 있었다. WAS는 비싸다. 스프링은 톰캣 같은 웹 컨테이너만 있어도 자카르타 EE의 기술들을 거의 다 쓸 수 있게 해준다는 의미다. 이 때문에 WAS 벤더들이 타격을 많이 받았다고 한다.
- 엔터프라이즈 개발을 쉽게: 복잡하고 실수하기 쉬운 로우레벨(플러밍)에 신경 쓰지 않고 비즈니스 로직에 전념하게 해준다. 다만 만능은 아니고 영업적인 멘트 느낌도 있다고 했다.
- 오픈소스지만 엔터프라이즈 서포트는 유료라서 계속 버전업이 이뤄진다.

### 스프링 삼각형

- POJO
  - Plain Old Java Object. JVM만 있으면 돌아가는 평범한 자바 객체.
  - 마틴 파울러가 만든 용어다. 예전에 EJB의 엔티티 빈, 세션 빈 같은 건 특정 클래스를 상속받아야 하고 무거웠는데, 그런 거 대신 일반 자바 객체에 비즈니스 로직을 넣는 게 더 효율적이라면서 만든 말이다.
  - 특정 프레임워크나 기술에 종속되지 않는다는 뜻이고, 스프링이 이걸 가져다 쓴다. 웹 컨테이너 없이 JVM만 있어도 된다.
- DI
  - 의존 관계를 클래스 안에서 직접 맺는 게 아니라 외부 설정 파일 같은 곳에서 동적으로 설정한다. A가 B를 의존해도 클래스 레벨에서는 그 부분을 최소화한다.
- AOP
  - 반복되는 공통 코드를 별도 모듈로 완전히 분리하고, 직접 호출하지 않아도 런타임에 그 공통 모듈이 자동으로 실행되게 해준다. 자세한 건 뒤에서 한다.
- PSA
  - 특정 DB나 특정 WAS에 종속되는 부분을 구현 클래스에 두고 인터페이스로 추상화해둔 것. 트랜잭션 처리 같은 것도 추상화돼 있어서 어떤 DB 연동 기술을 쓰든 개발자는 똑같은 방식으로 설정할 수 있다.
  - OXM(객체와 XML 매핑)도 여기에 있다. 자바 객체를 XML로, XML을 자바 객체로 바꾸는 건데 요즘은 XML보다 JSON을 많이 쓴다.

### JPA와 하이버네이트, 스프링 데이터 JPA

- JPA는 자카르타 EE에서 정의한 표준 스펙이다. 이런 기능이 있다고 정의만 한 명세.
- 하이버네이트는 JPA를 실제로 구현한 구현체다.
- 하이버네이트는 설정도 복잡하고 쓰기 까다로워서, 스프링 쪽에서 하이버네이트를 더 쉽게 쓰도록 한 번 더 추상화한 게 스프링 데이터 JPA다. 이건 나중에 배운다.

### 스프링의 모듈 구성

- 컨테이너, 컨텍스트, DAO, ORM, AOP, 웹 등으로 모듈이 나뉘어 있다.
- 스프링 프레임워크가 해주는 일 정리
  - 컨테이너 역할: 객체 생성과 라이프사이클 관리
  - DI 지원: 설정 파일이나 어노테이션으로 객체 간 의존 관계 설정
  - AOP 지원
  - POJO 형태로 작성 가능
  - 트랜잭션 처리를 어떤 기술이든 동일한 방식으로 설정
  - 영속성(앱이 종료돼도 정보가 남아 있는 것, 즉 DB) 관련 기술 연동 지원

## 2. XML, JSON, TOML, YAML, properties 비교

스프링 설정 파일을 만들기 전에 파일 형식들을 먼저 비교했다.

- XML
  - 확장 가능 마크업 언어. 시작 태그, 종료 태그 중심으로 데이터를 표현한다.
  - 태그가 반복돼서 문서가 장황하고 용량도 크고 읽는 데 시간이 걸린다. 필요한 데이터는 사실 값 몇 개인데 태그가 너무 많다.
  - 주석을 달 수 있고, 네임스페이스로 이름 충돌을 막을 수 있고, 속성도 줄 수 있다.
  - 문법에 굉장히 까칠해서 조금만 틀려도 설정 파일이 잘못되면 애플리케이션 실행 자체가 안 된다.
  - 읽는 파서로는 DOM, SAX 같은 게 있다. 예전에 공공기관, 금융기관 간 데이터 교환(SOAP)에 많이 썼다.
- JSON
  - 키와 밸류, 중괄호와 대괄호로 표현. 태그가 없어서 XML보다 간결하고 직관적이고 크기도 작다.
  - 특정 언어에 종속되지 않는다. REST API나 마이크로서비스 환경에서 사실상 표준.
  - 약점은 주석을 달 수 없다는 것.
- TOML
  - 사람이 직접 읽고 수정하기 좋은 설정 파일용 형식. 주석 지원. `[server]`, `[database]` 처럼 대괄호로 영역을 나눈다.
  - 데이터 교환보다는 설정 파일 용도로 쓴다. 코덱스 CLI 설정 파일이 이 형식이라고 한다.
- YAML
  - 들여쓰기로 구조를 표현한다. 쿠버네티스, 도커 컴포즈 같은 인프라 설정 파일에서 쓰고 스프링 부트 설정 파일로도 쓴다.
- properties
  - `키=값` 형태. 하위 속성을 나열할 때 `spring.application.name` 처럼 점을 계속 붙여서 길어질 수 있다.
  - YAML은 `spring:` 아래 두 칸, `application:` 아래 네 칸 이런 식으로 들여쓰기를 한다. 시각적으로 명확해서 중첩 설정은 한눈에 보기 좋은데 들여쓰기 칸이 안 맞으면 바로 에러가 난다.
- 정리
  - XML과 JSON은 데이터 교환과 설정 파일 둘 다 가능하다.
  - properties, YAML, TOML은 주로 설정 파일 용도다.
  - 스프링 프레임워크에서는 설정 파일로 XML을 쓰고, 값 설정은 전통적으로 properties를 많이 쓴다. 부트에서는 properties와 YAML 둘 다 쓴다.
- 설정 파일을 따로 만드는 이유: 이율 같이 자주 바뀌는 정보를 소스에 박아두면 바뀔 때마다 다시 컴파일해야 한다. 그래서 설정 파일에 빼놓는다.

## 3. IoC와 DI 개념

### IoC

- 제어권의 역전. 객체의 생성과 생명주기 관리에 대한 제어권이 개발자에서 프레임워크로 넘어갔다는 소프트웨어 공학 개념이고, 스프링이 이걸 채택했다.
- IoC는 크게 DL(룩업)과 DI로 나뉘는데 DL은 몰라도 된다고 했다. 스프링은 DI 방식을 쓴다.
- 보통은 A 클래스에서 B를 의존하면 `new B()`로 직접 생성하는데, 스프링에서는 컨테이너가 A, B를 각각 빈으로 만들어주고 A가 B를 참조할 수 있도록 레퍼런스를 넣어준다.
- A 클래스 안에는 B 타입 멤버 변수만 선언돼 있고, 컨테이너가 A에 생성자나 세터가 있는지 보고 B 객체를 생성해서 그 메서드 인자로 레퍼런스를 주입해준다.

### DI의 종류

- 세터 인젝션: 세터 메서드의 인자로 의존하는 객체 레퍼런스를 주입받는다.
- 생성자 인젝션: 생성자의 인자로 의존하는 객체 레퍼런스를 주입받는다.
- 일반 메서드를 통한 주입도 있긴 한데 우리는 세터와 생성자 두 가지만 쓴다.

### 용어 정리

- 스프링 빈: 스프링이 개발자 대신 생성하고 라이프사이클을 관리해주는 객체.
- 컨테이너: 빈을 생성하고 관리해주는 객체.
- 빈 팩토리: 스프링 빈 컨테이너에 접근하기 위한 가장 최상위 루트 인터페이스. `getBean` 메서드가 여기 있다.
- 애플리케이션 컨텍스트: 빈 팩토리의 하위 인터페이스. 빈 생성뿐 아니라 설정 파일(XML)을 읽어서 거기 적힌 대로 객체를 생성하는 역할까지 한다.
- 둘 다 컨테이너 역할을 하는 인터페이스다.
- 실제 구현 클래스는 많은데 우리는 웹이 아니고 XML 파일을 쓰니까 `GenericXmlApplicationContext`를 쓴다.
- 우리가 직접 객체를 만드는 게 완전히 없어지는 건 아니고, 컨테이너 객체는 우리가 직접 생성해줘야 한다.

### Hello와 Printer 구조 (다형성)

- `Hello`가 `Printer` 인터페이스를 의존하고, `StringPrinter`, `ConsolePrinter`가 `Printer`의 구현체다.
- `Hello` 소스 코드에는 `StringPrinter` 같은 구현 클래스 이름이 나오면 안 되고 상위 인터페이스인 `Printer` 타입만 적는다.
- 만약 소스에 구현 클래스 이름을 박아놓으면, 나중에 `ConsolePrinter`로 바뀔 때 소스를 고치고 재컴파일하고 테스트 다 새로 돌리고 결재를 다시 받아 배포해야 한다. 실제 돌아가는 업무 시스템에서는 굉장히 크리티컬하다.
- 그래서 `Hello`는 `Printer`만 의존한다고 코드에 쓰고, 실제로 어떤 구현체를 쓰는지는 XML에 적는다. 바뀌면 XML만 고치고 서버만 재시작하면 된다.
- `Hello`에는 이름과 프린터 필드, 세터 메서드가 있고 이 세터를 스프링이 호출해서 값을 넣어준다.

## 4. 스프링 설정 파일(XML) 작성

### 만들기

- `src/main/resources` 우클릭 > New > Spring Bean Configuration File 로 `spring-beans.xml`을 만들었다. 이름은 확장자만 xml이면 상관없다.
- 만들 때 네임스페이스에서 `beans`와 `context`를 체크하고 각각의 xsd를 선택한다. 의존성(스프링 컨텍스트)을 추가 안 하면 이 목록이 안 뜬다.
- 맥에서는 다른 프로젝트에 같은 이름 클래스가 있으면 자동완성에 같이 뜬다. 그럴 땐 내 프로젝트 쪽 클래스를 골라야 한다.

### 스키마(XSD)

- XML 스키마는 XML 문서의 설계도이자 검증 기준표다. 어떤 태그를 쓸 수 있는지, 부모와 자식 관계, 순서, 속성, 값의 데이터 타입 같은 규칙을 미리 정해둔 것이다.
- 우리 맘대로 쓰는 게 아니라 이 규칙에 맞춰서 써야 하고, 어기면 에디터에서 에러가 뜬다. 자동완성도 이 스키마 덕분이다.
- `beans` 스키마에서 `bean` 태그의 `id`, `class` 같은 속성이 정해져 있다.

### 태그 해석

<details>
<summary>빈 설정 XML 코드 보기</summary>

```xml
<!-- StringPrinter 클래스를 스프링 빈으로 설정 -->
<bean id="strPrinter" class="패키지명.StringPrinter" />

<!-- Hello 클래스를 스프링 빈으로 설정, 세터 인젝션 -->
<bean id="hello" class="패키지명.Hello">
    <property name="name" value="Spring" />
    <property name="printer" ref="strPrinter" />
</bean>
```

</details>

- `bean` 태그: 이 클래스를 스프링 빈으로 등록하라는 뜻. 컨테이너가 패키지명과 클래스명을 보고 클래스를 로딩해서 객체를 동적으로 생성한다. 하위 태그가 필요 없으면 `/>`로 닫는다. id는 소문자로 시작하고 중복되면 안 된다.
- `property` 태그: 세터 메서드를 매핑하는 태그. `name`은 세터 메서드 이름에서 `set`을 빼고 첫 글자를 소문자로 한 것이다. 예를 들어 `setPrinter`면 `printer`, `setMyPrinter`면 `myPrinter`.
- `value`: 문자열이나 숫자 같은 단순 값을 넣을 때.
- `ref`: 우리가 만든 객체(다른 빈)를 참조할 때. 참조할 빈의 id를 적는다. `ref="strPrinter"`면 `strPrinter` 빈, 즉 `StringPrinter` 객체의 레퍼런스를 `setPrinter`에 넣어준다.
- 세터가 없는 이름을 `name`에 쓰면 에러가 난다. 세터를 주석 처리해보니 바로 에러가 뜨는 걸 확인했다.

### 컨테이너가 하는 일 순서

1. 컨테이너가 XML을 읽는다.
2. `bean` 태그를 보고 `Hello`, `StringPrinter` 객체를 생성한다.
3. `property` 태그를 만나면 해당 세터가 있는지 확인한다. 없으면 에러.
4. `setName`을 호출하면서 문자열 `Spring`을 넣는다. 결국 `Hello` 객체의 `name` 변수에 `Spring`이 들어간다.
5. `setPrinter`를 호출하면서 `strPrinter` 빈의 레퍼런스를 넣는다. 결국 런타임에 `Hello`는 `StringPrinter`를 의존하게 된다. 이게 세터 인젝션이다.

### 실습에 쓴 클래스 구조

생성 시점과 세터 호출 시점을 눈으로 보려고 생성자와 세터에 로그를 넣었다.

<details>
<summary>Hello 클래스 코드 보기</summary>

```java
public class Hello {
    private String name;
    private Printer printer;

    public Hello() {
        System.out.println(this.getClass().getName() + " 기본 생성자 호출");
    }

    public Hello(String name, Printer printer) {
        this.name = name;
        this.printer = printer;
        System.out.println(this.getClass().getName() + " 인자 있는 생성자 호출");
    }

    public void setName(String name) {
        System.out.println(this.getClass().getName() + " setName 호출");
        this.name = name;
    }

    public void setPrinter(Printer printer) {
        System.out.println(this.getClass().getName() + " setPrinter 호출");
        this.printer = printer;
    }

    public String sayHello() {
        return "Hello " + name;
    }

    public void print() {
        this.printer.print(sayHello());
    }
}
```

</details>

- `StringPrinter`는 `Printer`를 구현하고 `print(message)`가 메시지를 `StringBuffer`에 append하고, `toString()`은 쌓인 문자열을 반환한다.
- `ConsolePrinter`는 `print(message)`에서 콘솔에 출력한다.
- 두 구현체 모두 생성자에 로그를 넣어서 언제 객체가 생성되는지 확인했다.

## 5. pom.xml과 의존성

- `pom.xml`은 프론트의 `package.json`과 비슷한 역할이다.
- 자바 버전은 `1.8`(맥은 `11`). 스프링 5 버전이 JDK 8에 맞는 버전이라 스프링 5를 쓴다. 릴리즈라고 붙은 버전이 안정된 버전이다.
- 의존성은 메이븐 레포지토리 사이트에서 라이브러리를 검색해서 나오는 `dependency` 태그를 복사해서 `dependencies` 안에 넣는다. 센트럴 레포지토리에 있는 건 그냥 받으면 된다. 다른 저장소를 쓰면 따로 적어줘야 한다.
- 스프링 버전을 properties에 한 번만 적어두고 `${spring.version}` 으로 치환해서 쓴다. 의존성이 계속 추가돼도 버전을 바꾸고 싶을 때 한 군데만 고치면 된다.
- 스프링 컨텍스트 하나만 추가해도 그게 의존하는 aop, core 등의 jar가 같이 내려와서 메이븐 디펜던시즈에 보인다.
- 그레이들이라는 빌드 도구도 있다. 메이븐이 원조 격이고 그레이들이 그걸 더 빠르게 개선한 것이다.
- 추가한 의존성
  - 스프링 컨텍스트: 빈 팩토리, `GenericXmlApplicationContext` 같은 걸 쓰기 위해 필요
  - JUnit5(주피터): 테스트용. scope를 `test`로 줬다.
  - 스프링 테스트: scope `test`
- scope가 `test`라는 건 그 라이브러리가 `src/test` 아래에만 적용된다는 뜻이다. 그래서 테스트 케이스는 반드시 `src/test/java` 밑에 만들어야 한다. compile scope는 생략해도 된다.

## 6. JUnit5로 단위 테스트

### 개념

- 단위 테스트는 함수나 메서드가 제대로 작성됐는지 검증하는 절차다. 메인 메서드 있는 클래스를 만들어서 확인해도 되지만, 단위 테스트 프레임워크를 쓰는 게 낫다.
- JUnit은 켄트 백(TDD)과 에릭 감마(디자인 패턴, 이클립스)가 만들었고 자바에 특화된 단위 테스트 프레임워크다. 5버전은 주피터라고도 부른다.
- 테스트 메서드 위에 `@Test` 어노테이션을 붙여야 실행이 된다. 안 붙이면 실행이 안 되니까 어노테이션을 먼저 붙이고 메서드를 선언하면 실수를 덜 한다.
- 각 테스트 메서드를 호출할 때마다 새 인스턴스를 만들어서 테스트가 독립적으로 이뤄진다.
- `Assertions`에 `assert`로 시작하는 정적 메서드가 많다. 실제 결과와 기대값을 비교해서 판별하는 용도다.
  - `assertEquals(expected, actual)`: 값 비교
  - `assertSame(expected, actual)`: 주소(레퍼런스) 비교
  - 그 외 `assertNotEquals`, `assertNotNull` 등
- 정적 메서드는 원래 `Assertions.assertSame(...)`처럼 클래스명을 붙여야 하는데, 자바 5부터 나온 static import로 `import static org.junit.jupiter.api.Assertions.*;` 를 쓰면 클래스명을 생략할 수 있다. 성능 차이는 없다.
- 자동 임포트는 `Ctrl+Shift+O`.

### 테스트 클래스 만들기

- `src/test/java` 아래에 테스트 대상과 똑같은 패키지를 만들고, 거기에 `HelloBeanJUnitTest` 클래스를 만들었다. 메인 메서드는 필요 없다.

### 컨테이너 생성과 빈 요청

<details>
<summary>테스트 클래스 코드 보기</summary>

```java
public class HelloBeanJUnitTest {
    BeanFactory factory;

    @BeforeEach
    void init() {
        factory = new GenericXmlApplicationContext("classpath:spring-beans.xml");
    }

    @Test
    void hello() {
        // 아이디로만 요청하면 Object가 리턴돼서 캐스팅 필요
        Hello hello = (Hello) factory.getBean("hello");

        // 아이디와 타입을 같이 주면 캐스팅 필요 없음 (이쪽을 권장)
        Hello hello2 = factory.getBean("hello", Hello.class);

        // 주소 비교
        assertSame(hello, hello2);

        // 세터 인젝션 검증 1: name
        assertEquals("Hello Spring", hello.sayHello());

        // 세터 인젝션 검증 2: printer
        hello.print();   // 먼저 호출해줘야 버퍼에 쌓임
        Printer printer = factory.getBean("strPrinter", Printer.class);
        assertEquals("Hello Spring", printer.toString());
    }
}
```

</details>

- `new Hello()` 대신 컨테이너를 만들고 컨테이너에게 `getBean`으로 달라고 요청하는 방식이다.
- 컨테이너를 만들 때 XML 파일 위치를 반드시 알려줘야 한다. 그래야 컨테이너가 XML을 파싱해서 거기 적힌 대로 객체를 생성하고 의존 관계를 맺어준다.
- `GenericXmlApplicationContext`를 `BeanFactory`로 받아도 되고 `ApplicationContext`로 받아도 된다.
- 컨테이너 생성 코드는 `@BeforeEach` 메서드로 뺐다. `@BeforeEach`가 붙은 메서드는 각 테스트 메서드가 실행되기 전에 먼저 호출된다. 반대로 `@AfterEach`는 실행 후에 호출된다. 메서드 이름은 중요하지 않고 어노테이션이 중요하다. 변수 선언은 클래스 위로 올리고 생성은 메서드 안에서 한다. 변수를 메서드 안에서 타입까지 같이 쓰면 새 변수가 돼버리니까 타입은 지워야 한다.
- 타입은 `StringPrinter.class`가 아니라 상위 인터페이스인 `Printer.class`로 줘도 되고 받을 때도 `Printer`로 받아도 된다. 어차피 `StringPrinter`도 `Printer` 타입이라서(다형성).

### 실행해서 알게 된 것

- 콘솔 로그를 보니 컨테이너가 XML을 읽어서 그 순서대로 객체를 생성하고 세터 메서드까지 호출해준다는 걸 알 수 있었다. 우리는 객체 생성을 직접 안 했다.

### classpath가 뭔지

- 개발할 때는 `src/main/java`, `src/main/resources`로 나뉘어 보이지만 컴파일되면 `target/classes` 폴더 밑에 클래스 파일과 XML 파일이 같이 놓인다.
- 이 `classes` 폴더를 클래스패스라고 부르고 XML이 바로 그 밑에 있어서 `classpath:spring-beans.xml` 로 적는다.

### 값 검증할 때 주의한 점

- `assertEquals`로 값을 비교하면 공백 한 칸 차이도 걸러낸다.
- printer 검증이 좀 복잡했다. `setPrinter`가 제대로 주입됐는지 보려면
  1. `hello.print()`를 먼저 호출한다. 그러면 `this.printer`가 가리키는 `StringPrinter`의 `print`가 호출돼서 `Hello Spring`이 버퍼에 쌓인다.
  2. `StringPrinter` 빈을 `getBean`으로 따로 가져온다. 이건 `Hello`와 다른 빈이다.
  3. `toString()`을 호출한 결과가 `Hello Spring`인지 비교한다.
- 싱글톤이라 같은 `StringPrinter` 객체가 `Hello`에 주입된 것과 `getBean`으로 가져온 것이 같아서 이렇게 확인이 된다.
- 이렇게 JUnit만 쓰면 컨테이너를 직접 만들고 `getBean`을 계속 해야 하는 게 불편해서, 뒤에서 스프링 테스트를 쓴다.

## 7. 싱글톤과 빈의 스코프

### 확인

- `getBean`을 두 번 요청해서 주소를 비교했더니 같았다(`assertSame` 성공). 스프링 컨테이너는 빈을 한 번만 생성해서 계속 재사용한다는 걸 알 수 있다. 싱글톤 패턴이 적용돼 있다.

### 싱글톤 패턴

- GoF 디자인 패턴 중 생성 패턴에 속한다. 인스턴스를 하나만 생성하도록 보장하고 그걸 재사용하는 패턴이다.
- 구현하려면 생성자를 `private`으로 막아서 외부에서 `new`를 못 하게 하고, `private static` 변수로 내부에서 객체를 만들고, `static getInstance()`로 그 객체를 반환한다. 멀티스레드 환경에서 동시에 접근할 때 두 개 이상 생성되는 문제도 신경 써야 한다.
- 장점은 불필요한 객체 생성을 막아서 메모리를 아끼는 것이다. 웹 애플리케이션에서 UI 요청이 올 때마다 컨트롤러, 서비스, 리포지토리 객체를 새로 만들면 힙 메모리 낭비와 가비지 컬렉션 부하가 커진다.
- 스프링을 안 쓰면 싱글톤 패턴이 뭔지 알고 클래스를 그렇게 작성해야 하는데, 이건 업무 로직이 아니라 성능과 관련된 얘기다. 이런 걸 스프링이 컨테이너 메커니즘으로 대신 해준다. 이게 플러밍에 포커싱한다는 말이다. 개발자는 클래스를 싱글톤으로 작성하지 않아도 된다.
- 서버 프로세스와 스레드: 서버를 띄우면 자바 프로세스가 하나 뜨고 클라이언트 요청마다 스레드가 처리한다. 싱글톤 빈은 그 프로세스 안에서 하나만 만들어두고 여러 스레드가 공유한다.

### 스코프

- 빈의 스코프는 빈이 유효한 범위. `bean` 태그의 `scope` 속성으로 설정한다.
- singleton: 기본값. 같은 id로 `getBean`을 호출하면 항상 같은 인스턴스를 반환한다. 설정 안 하면 싱글톤이다.
- prototype: `getBean`을 요청할 때마다 매번 새 객체를 생성한다. `scope="prototype"`으로 바꾸고 테스트를 돌렸더니 `assertSame`이 실패했고, 두 빈의 해시코드가 다르게 나왔다. 다시 싱글톤으로 되돌렸다.
- 웹 환경에서는 request와 session 스코프가 있다.
  - session: 브라우저를 열고 있는 동안 계속 같은 빈을 사용
  - request: 링크를 눌러 요청이 날아가는 한 번의 요청 범위. session보다 훨씬 좁다.
- 프로토타입이 필요한 경우는 빈별로 독립적인 상태를 가져야 하는 경우 같은 때다. 상태가 없는 객체는 싱글톤이 기본이고 대부분 싱글톤으로 쓴다. 프로토타입은 라이프사이클을 컨테이너가 끝까지 관리하지 않아서 자원 해제 코드를 따로 작성해야 한다.

## 8. 생성자 인젝션

- 세터 인젝션은 기본 생성자로 객체를 만들고 세터를 두 번 호출하는 방식이다. 생성자 인젝션은 인자가 두 개인 오버로딩된 생성자를 호출하면서 한 번에 초기화하는 방식이다. 1일차에 `Account` 예제로 했던 게터, 세터와 오버로딩 생성자랑 똑같은 얘기다. 스프링은 객체 생성을 우리가 안 하니까 XML 설정 같은 게 복잡해 보이는 것뿐이다.
- 기본 생성자가 없어서 인자 있는 생성자만 있는 클래스라면 세터 인젝션은 못 쓰고 생성자 인젝션만 쓸 수 있다. 기본 생성자를 주석으로 막아보니 세터 인젝션 쪽에서 기본 생성자가 없다는 에러가 났다.

<details>
<summary>생성자 인젝션 XML 코드 보기</summary>

```xml
<bean id="helloConst" class="패키지명.Hello">
    <constructor-arg index="0" value="Spring" />
    <constructor-arg index="1" ref="콘솔프린터빈id" />
</bean>
```

</details>

- `constructor-arg` 태그로 생성자 인자를 넣는다.
  - `index`: 인자 순서. 0부터 시작.
  - 인덱스 대신 `name` 속성으로 생성자 인자 변수 이름을 줄 수도 있다. 타입은 안 되고 이름이다.
  - 단순 값은 `value`, 다른 빈은 `ref`.
- 빈 id는 중복되면 안 돼서 세터 인젝션용 `hello`와 구분해서 `helloConst`처럼 따로 줬다.
- 이번에는 `ConsolePrinter`를 참조하게 했다.
