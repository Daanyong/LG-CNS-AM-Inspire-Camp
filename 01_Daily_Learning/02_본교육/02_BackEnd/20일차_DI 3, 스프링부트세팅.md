## 1. DI 전략 세 가지 흐름

- 전략 1: 빈 정의와 의존 관계 설정을 전부 XML 에 적음. 여러 명이 설정 파일을 같이 쓰면 공유 문제가 불편했던 방식
- 전략 2: 클래스에 `@Component` 같은 어노테이션을 붙이고 XML 에는 컴포넌트 스캔만 적음. 실무에서는 XML 과 어노테이션을 섞어 쓰는 경우가 제일 많음
- 전략 3: XML 을 아예 안 쓰고 자바 클래스(설정 클래스)가 XML 역할을 대신함. 스프링 부트가 이 방식

처음부터 부트로 가서 "`@Configuration` 이 설정 클래스고 `@ComponentScan` 이 스캔이다" 라고만 하면 이해가 안 되니까, 금요일부터 단계별로 이 종착점까지 온 거라고 하셨다. 부트는 이 과정이 다 자동으로 되어 있어서 내부 원리를 이해하는 데 도움이 된다.

## 2. 스테레오타입 어노테이션과 계층 구조

### 어노테이션 종류

- `@Component`: 가장 범용적인 스프링 빈 선언
- `@Repository`: DB 와 연동하는 영속성 계층 클래스. 기능은 `@Component` 와 같지만 역할이 드러나게 쓰는 것
- `@Service`: 비즈니스 로직이나 트랜잭션 처리를 담당하는 클래스
- `@Controller`: 웹 요청을 받아 타임리프 같은 뷰 페이지로 응답하는 클래스
- `@RestController`: 뷰 대신 JSON 데이터를 내려주는 REST API 용 컨트롤러

결국 전부 `@Component` 를 구체화한 것이고, 역할에 맞게 골라 쓰는 것.

### 왜 서비스와 레파지토리를 나누나

- 대출 이자 계산, 신용 점수 계산 같은 비즈니스 로직은 일관되게 가지만 DB 는 RDB 에서 NoSQL(MongoDB 등)로 바뀔 수도 있음
- 그래서 로직 클래스와 DB 연동 클래스를 분리하는 것. 단일 책임 원칙과 이어지는 이야기
- 트랜잭션도 DB 연동에서 데이터 일관성을 지키기 위한 설정이라 서비스 쪽에 둠

### 계층형 구조

- 프레젠테이션 계층(컨트롤러) → 서비스 계층(서비스) → 데이터 접근 계층(레파지토리, DAO) → DB
- DAO 는 Data Access Object. XML 로 SQL 을 쓰는 건 MyBatis 인데 우린 안 쓰고 JPA 를 쓸 예정
- 핸들러 매핑, 디스패처 서블릿, 뷰 리졸버는 스프링이 제공하니까 우리는 컨트롤러, 서비스, 레파지토리만 구현하면 됨 (내부 구조는 나중에)
- JSP 는 오래된 서버사이드 템플릿 엔진이라 안 쓰고 타임리프를 쓸 예정. 넥스트JS 가 자바스크립트 기반 SSR 이라면 타임리프는 자바 기반 서버사이드 렌더링 템플릿 엔진

### 주입 관련 어노테이션

- `@Autowired`: 타입 기반 주입. 생성자, 필드, 메서드 등 다양한 곳에 붙일 수 있고 스프링에서 만든 것
- `@Resource`: 이름(id) 기반 주입. 필드와 세터에만 적용되고 자카르타 EE(JSR-250) 쪽 표준
- `@Qualifier`: 특정 빈을 지목할 때 `@Autowired` 와 같이 씀. 단독으로는 거의 안 씀
- `@Value`: 단순한 값을 주입할 때 사용

## 3. 전략 3: 자바 설정 클래스

### 핵심 어노테이션

- `@Configuration`: 이 클래스가 설정 클래스라는 표시. 설정 역할이라 다른 `@Component` 류보다 메모리에 먼저 올라가야 해서 반드시 붙여야 함
- `@ComponentScan(basePackages = "...")`: XML 의 `context:component-scan` 대응. 스캔할 패키지 지정. 속성 이름이 `basePackages` 처럼 중간 대문자인 점 주의
- `@PropertySource("classpath:...")`: XML 의 `property-placeholder` 대응. properties 파일 위치 알려줌
- `@Bean`: 메서드 안에서 직접 객체를 만들고 그 반환값을 스프링 빈으로 등록

### 두 가지 설정 클래스의 차이

- 클래스에 이미 `@Component`, `@Autowired`, `@Value` 같은 어노테이션이 붙어 있는 경우(전략 2 대상): 설정 클래스에는 `@Configuration` + `@ComponentScan` + `@PropertySource` 만 쓰면 끝. 스캔이 알아서 빈으로 등록해줌
- 어노테이션이 하나도 없는 순수 클래스인 경우(전략 1 대상): 스캔할 표시가 없으니까 설정 클래스 안에서 `@Bean` 메서드로 객체를 직접 만들어서 빈으로 만들어줘야 함

스프링 부트에서는 두 방식을 다 쓴다고 한다. 부트는 `@ComponentScan` 도 메인 애플리케이션 클래스에 이미 들어 있어서 직접 안 써도 되고 properties 파일도 알아서 읽어준다.

### `@Bean` 메서드 규칙

- 메서드 이름이 빈의 id 가 됨. 그래서 이름만 다르게 지으면 `@Qualifier` 없이도 구분됨
- 반환 타입은 `Printer` 처럼 상위 인터페이스 타입으로 하는 게 좋음
- `@Bean(name = "...")` 로 id 를 따로 줄 수도 있지만 굳이 안 해도 됨
- 스코프를 안 적으면 기본이 싱글톤. 바꾸고 싶으면 `@Scope("prototype")` 처럼 value 나 scopeName 속성을 줌

### `@Bean` 이 왜 필요한가, `@Component` 와 차이

- 둘 다 스프링 빈을 만든다는 점은 같음
- `@Component` 는 클래스 위에 붙이고 `@Bean` 은 메서드 위에 붙임
- 결정적인 차이는 내가 수정할 수 없는 클래스일 때. 예를 들어 Swagger(REST API 문서를 화면으로 만들어주고 브라우저에서 바로 테스트할 수 있게 해주는 도구) 라이브러리 안의 `Docket` 클래스를 스프링 빈으로 쓰고 싶다고 하면, 라이브러리 소스를 열어서 `@Component` 를 붙일 수가 없음
- 이때 내 설정 클래스에 메서드를 만들고 안에서 `Docket` 객체를 생성한 뒤 `@Bean` 을 붙이면 스프링 빈이 됨 (싱글톤이라 한 번 만들고 재사용)
- 부트는 DB 연동 같은 외부 라이브러리를 많이 쓰기 때문에 이런 경우가 잦다고 함. 지금 당장 이해 안 돼도 나중에 하다 보면 알게 된다고 하셨다

### 컨테이너 종류가 달라진다

- XML 로 설정할 때 컨테이너 클래스는 `GenericXmlApplicationContext`
- 설정 클래스를 쓸 때는 `AnnotationConfigApplicationContext` 가 컨테이너 역할
- 그래서 스프링 테스트에서 이 컨테이너를 로딩하는 `AnnotationConfigContextLoader` 를 `@ContextConfiguration` 의 `loader` 로 지정함
- JUnit4 에서는 필수이고 JUnit5 에서는 자동 인식해서 생략 가능. 컨테이너 종류가 바뀐다는 걸 보여주려고 일부러 적어본 것
- `@ContextConfiguration` 의 `locations`(XML 경로) 대신 `classes`(설정 클래스)를 쓴다는 것도 달라진 점

### 만든 것 정리

- 어노테이션이 붙은 클래스용 설정 클래스 `HelloBeanConfig`: `@Configuration`, `@ComponentScan`, `@PropertySource` 만 사용
- 순수 클래스용 설정 클래스 `HelloConfig`: `Printer` 두 종류와 `Hello` 를 `@Bean` 으로 직접 생성
- 각각에 대한 테스트 클래스를 만들어서 주입이 잘 되는지, 값이 제대로 들어왔는지 확인함

```java
@PropertySource("classpath:value.properties")
public class HelloBeanConfig {
    // XML 에서 하던 컴포넌트 스캔, 프로퍼티 플레이스홀더 역할을 어노테이션이 대신함
}
```

```java
@ExtendWith(SpringExtension.class)
@ContextConfiguration(
        classes = HelloBeanConfig.class,
        loader = AnnotationConfigContextLoader.class // JUnit5 에서는 생략 가능
)
class AnnotatedHelloBeanConfigTest {

    @Autowired
    Hello hello;

    @Resource(name = "stringPrinter")
    Printer printer;

    @Test
    void helloTest() {
        assertEquals("Hello Spring", hello.sayHello());
        hello.print();
        assertEquals("Hello Spring", printer.toString());
    }
}
```

<details>
<summary>순수 클래스용 설정 클래스 (@Bean 으로 직접 생성)</summary>

```java
@Configuration
@PropertySource("classpath:values.properties")
public class HelloConfig {

    @Autowired
    Environment env;

    // 메서드 이름이 빈 id 가 된다
    @Bean
    public Printer stringPrinter() {
        return new StringPrinter();
    }

    @Bean
    public Printer consolePrinter() {
        return new ConsolePrinter();
    }

    // 기본 생성자 + 세터 주입
    @Bean
    @Scope("singleton") // 기본값이라 안 적어도 싱글톤
    public Hello hello() {
        Hello hello = new Hello();
        hello.setName(env.getProperty("xml.name"));  // properties 에서 읽어옴
        hello.setPrinter(stringPrinter());           // 메서드 호출 결과가 주입됨
        return hello;
    }

    // 오버로딩된 생성자 주입
    @Bean
    public Hello helloCons() {
        String consName = env.getProperty("xml.cons.name");
        return new Hello(consName, consolePrinter());
    }
}
```

</details>

```java
    }
}
```

## 4. properties 값 읽는 방법

자주 바뀌는 값은 소스에 박지 말고 properties 파일로 빼는 게 관례. 개발 중엔 자동 컴파일이라 부담이 없어도 운영에서는 소스를 고쳐서 다시 빌드하는 게 큰 리스크라서 그렇다고 함.

- `@Value("${키}")`: 필드나 메서드 파라미터에 붙여서 값 주입. `${}` 로 감싸야 하고, 키를 잘못 쓰면 문제가 생기니 조심
- `Environment` 인터페이스: 현재 실행 중인 애플리케이션의 환경 정보를 담고 있고 `getProperty("키")` 로 값을 읽음. 상위 인터페이스인 `PropertyResolver` 에 `getProperty` 가 있음
- `Environment` 는 인터페이스지만 `@Autowired` 만 붙이면 구현 클래스가 뭔지 몰라도 스프링이 객체를 만들어서 넣어줌 (프린터 인터페이스 주입받는 거랑 같은 원리)
- `@Value` 는 클래스 필드에 붙이는 방식이라 메서드 안에서 읽을 때는 `Environment` 가 편해서 이쪽을 씀
- `Environment.getProperty` 는 키 이름이 틀려도 에러 없이 그냥 값을 못 가져오는(null) 식으로 동작함
- XML 안에서도 `property-placeholder` 의 `location` 으로 파일을 지정해두면 `value="${키}"` 형태로 값을 읽을 수 있음. 일부러 처음엔 안 했던 거고 연습문제 풀이 때 다시 해봄

## 5. 세터 주입과 생성자 주입

- 세터 주입은 기본 생성자로 객체를 만든 다음 `setXxx` 로 값을 넣는 방식
- 생성자 주입은 인자가 있는 생성자를 호출하면서 값을 넣는 방식
- `Hello` 에 기본 생성자와 오버로딩된 생성자가 둘 다 있으면 둘 중 아무거나 써도 되지만, 기본 생성자가 없고 인자 있는 생성자만 있다면 생성자 주입이 선택이 아니라 필수가 됨
- 자바 설정 클래스에서는 `new Hello(이름, 프린터)` 처럼 인자를 직접 넘기면 됨. 두 번째 인자인 `consolePrinter()` 는 반환 타입이 `Printer` 라서 변수에 안 담고 바로 넣어도 됨
- 같은 타입 빈이 여러 개(`hello`, `helloCons`)면 테스트에서 `@Resource(name = "...")` 로 빈 id 를 지정해서 받음

## 6. 스프링 부트 개요

### 한 줄로

- 스프링 기반 애플리케이션을 최소한의 설정으로 바로 실행하고 운영에 적용할 수 있게 만든 것

### 특징 정리

- 오피니언 에이티드: 직역하면 "자기 주장이 강한" 인데, 부트 개발자들이 자주 쓰일 만한 서드파티 라이브러리를 미리 골라서 기본 설정까지 해놨다는 뜻. 예를 들어 로깅은 Logback, JSON 처리는 Jackson, 커넥션 풀은 HikariCP. 덕분에 개발자는 최소한의 혼란으로 빨리 시작할 수 있음
- 서드파티: 스프링 입장에서 외부 라이브러리 (MongoDB, Kafka, Hibernate, Jackson, Flyway, GraphQL, Neo4j 등)
- 단독 실행: 톰캣이 내장(임베디드)되어 있어서 war 로 안 묶고 jar 로 묶어서 자바 앱처럼 그냥 실행할 수 있음
- 스타터 의존성: 자주 쓰는 라이브러리 묶음을 `spring-boot-starter-xxx` 하나로 가져오는 것. 빌드 설정이 단순해짐 (예: `starter-data-jpa`)
- 자동 설정: 외부 라이브러리를 쓸 때 필요한 설정 클래스(`...AutoConfiguration`)를 부트가 이미 다 만들어놨고 자동으로 등록됨. 전략 3 에서 만든 설정 클래스를 부트가 대신 만들어준 셈
- 운영 준비 기능: 액추에이터로 헬스 체크, 메트릭, 설정 정보 같은 모니터링 기능을 바로 쓸 수 있음. 나중에 마이크로서비스 할 때 중요
- XML 없음: 설정을 XML 로 하지 않고 전부 설정 클래스로 함

프레임워크 단계에서 DI 를 이틀 반이나 설명한 이유가 이거라고 하셨다. 부트 안에 응축돼 있는 게 많아서 DI 개념을 확실히 알아야 내부가 이해된다고.

## 7. Spring Initializr 로 프로젝트 만들기

### 설정한 값

- Project: Maven
- Language: Java
- Spring Boot: 4.0.x (스냅샷 아닌 안정 버전)
- Group: `com.inspirecamp7` 같은 형태 (그룹명이 패키지명 기준이 됨)
- Artifact: 프로젝트 폴더명이 되고 zip 파일 이름에도 들어감. 패키지명은 소문자로 맞춰야 해서 Artifact 와 패키지명을 따로 신경 써야 했음 (Artifact 를 바꾸면 패키지명이 같이 바뀌는 버그가 있어서 마지막에 다시 확인)
- Packaging: Jar
- Configuration: Properties
- Java: 17

### 추가한 의존성

- Spring Web: 웹 앱 개발, 내장 톰캣, 동기 방식 (WebFlux 같은 비동기 방식은 안 씀)
- Spring Data JPA: 하이버네이트 기반 영속성 처리
- H2 Database: 자바로 만든 가벼운 인메모리 DB. 로컬 개발과 테스트용
- MariaDB Driver: 첫날 설치한 MariaDB 에 연결하기 위한 JDBC 드라이버
- Thymeleaf: JSP 를 대체하는 서버사이드 템플릿 엔진. `.html` 확장자를 쓰고 jar 로도 잘 동작
- Validation: 서버 쪽 입력값 검증. 프론트의 자바스크립트 검증은 개발자 도구에서 코드가 다 보여서 우회가 가능하니 백엔드에서도 검증해야 안전함. 하이버네이트 Validator 로 구현된 빈 밸리데이션
- Spring Boot DevTools: 소스를 고치면 자동 재시작되고 라이브 리로드까지 해주는 개발 편의 도구. 없으면 매번 애플리케이션 클래스를 내렸다 올려야 해서 불편함 (FastAPI 의 reload 옵션이나 Vite 와 비슷한 느낌)
- Lombok: getter, setter, toString, 생성자, 빌더 같은 보일러플레이트 코드를 어노테이션만으로 자동 생성
- Spring Boot Actuator: 헬스 체크, 메트릭, 로그 제어 같은 모니터링 정보를 HTTP 엔드포인트로 제공. 결과가 JSON 으로만 나옴
- Spring Boot Admin Client: 서드파티(코드센트릭) 오픈소스. 액추에이터가 내놓는 JSON 을 대시보드로 시각화해주는 Admin 서버가 있고, 우리가 만드는 앱은 모니터링 대상이 되는 클라이언트 쪽. 

### 기타

- Generate 하면 zip 이 받아지고, Explore 로 만들어질 `pom.xml` 을 미리 볼 수 있음
- Share 로 설정이 담긴 링크를 만들어서 공유하면 같은 설정이 그대로 채워짐
- zip 은 이미 프로젝트 폴더가 들어 있어서 압축 풀 때 폴더가 한 번 더 겹치지 않게 주의. 풀고 나서 바로 `.mvn` 폴더가 보여야 정상

## 8. IntelliJ 설정과 트러블슈팅

### 프로젝트 열기와 JDK 설정

- IntelliJ IDEA 를 실행해서 압축 푼 프로젝트 폴더를 Open
- File > Project Structure 에서 Project SDK 가 No SDK 로 되어 있으면 Add SDK > Add JDK from disk 로 JDK 17 경로를 지정. Language level 은 SDK default

### 빌드 에러

- 처음에 Build > Rebuild Project 를 했더니 의존성을 못 가져오고 에러가 나옴. 
- Boot 4.0 대로 넘어오면서 생긴 의존성 관리 문제
  - `.mvn/wrapper/maven-wrapper.properties` 의 Maven 버전을 3.9.11 로 변경 (기존 3.10 쪽 버전에서 문제가 있었음)
  - `pom.xml` 의 스프링 부트 버전을 4.0.6 으로 변경 (처음 선택한 패치 버전에 문제가 있었음)
  - 수정 후 `pom.xml` 에 뜨는 Maven 리로드 아이콘(m 표시)을 반드시 눌러서 의존성을 다시 받음
  - 보안 취약점(CVE) 경고 22개는 워닝이라 일단 넘어감
- File > Settings > Build, Execution, Deployment > Compiler > Java Compiler 에서 Project bytecode version 을 17 로 하고, Per-module bytecode version 에 모듈을 추가(+ 버튼)해서 거기도 17 로 설정 후 Apply
- 다시 Build > Rebuild Project 해서 에러 없이 빌드되면 성공
