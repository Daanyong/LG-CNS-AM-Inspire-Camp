## shadcn 버튼 커스텀

shadcn으로 버튼을 설치하면 `components/ui/button.tsx`가 생긴다. 근데 여기를 직접 고치면 나중에 shadcn을 다시 설치할 때 덮어써져서 수정한 게 날아간다.

그래서 방법은 두 가지다.

1. 원본을 복사해서 `atoms` 아래에 `CustomButton` 같은 이름으로 따로 만들기
2. 쓰는 쪽에서 `className`으로 덮어쓰기

이름을 그대로 `Button`으로 두면 import 경로가 헷갈릴 수 있다. 강사님도 이름 겹치는 게 제일 위험하다고 하셨다. 실제로 수업 중에 shadcn 버튼이 계속 잡혀서 스타일이 안 먹었다.

Tailwind 최신 버전에서는 색을 `tailwind.config`에 등록하지 않고 CSS의 `:root`에 `--primary` 같은 변수로 선언하면 바로 쓸 수 있다. 다크 모드 색도 같이 정의해두면 된다.

사이즈는 `h-9` 같은 게 높이고 `px-5` 같은 게 좌우 폭이다. 설정을 바꿨는데 반영이 안 되면 dev 서버 새로고침을 한다.

중요 사항
- shadcn 기본값은 건드리지 말 것
- 디자인이 shadcn이랑 완전히 다르면 굳이 가져와서 고치지 말고 직접 만들 것
- shadcn 버튼을 보고 비슷하게 내가 만들 수 있으면 그게 실력. 그러니 shadcn 코드를 많이 읽어볼 것

## Input 컴포넌트

`npx shadcn@latest add input`으로 설치한다. 터미널을 새로 열면 항상 상위 폴더에서 시작해서, Next 프로젝트 폴더로 `cd` 하고 설치해야 한다.

input.tsx는 코드가 복잡해 보여도 TypeScript 타입 때문이고, 실제로는 input 속성 몇 개 넘겨주는 게 전부다. children이 없다는 것도 확인했다. 모바일에서는 숫자만 입력해야 하면 키보드 타입을 지정해서 숫자 패드가 뜨게 하는 게 좋다고 한다.

## 상태로 관리 vs form action

이게 오늘 제일 중요한 내용이었다.

### 리액트 방식

`useState`로 아이디/비밀번호를 들고 있다가 `onChange`로 채우고, 버튼 누르면 객체로 묶어서 POST로 보낸다.

### Next가 원하는 방식

```tsx
async function login(formData: FormData) {
  'use server'
  const userId = formData.get('userId')
  const password = formData.get('password')
}

<form action={login}>
  <input name="userId" />
  <input name="password" type="password" />
  <button type="submit">로그인</button>
</form>
```

`onSubmit`이 아니라 `action`으로 넘기고, 값은 `name` 속성 기준으로 FormData에 담겨서 간다. 그래서 name이 꼭 필요하다.

- 클라이언트 방식은 브라우저 콘솔에 로그가 찍히고, 네트워크 탭에서 아이디/비밀번호가 Payload로 다 보인다
- 서버 액션 방식은 터미널(서버 콘솔)에만 찍히고, 브라우저에는 값이 안 남는다
- 서버 액션은 브라우저에서 Next 서버를 거쳐 API로 가니까 보안 면에서 낫다. 대신 입력 중 감지(`onChange`)가 안 되니까 필요하면 클라이언트 컴포넌트를 같이 써야 해서 구조가 복잡해진다

참고로 shadcn의 `Form`, Next의 `Form`, 리액트의 `Form`이 다 있어서 import를 잘못하면 엉뚱한 게 불릴 수 있다. 이런 API는 자주 바뀌니까 공식 문서를 확인하는 습관을 들일 것.

### page.tsx의 역할

page는 "이 주소는 이런 페이지"라고 선언하는 정도의 역할만 하고, 나머지 기능은 컴포넌트로 빼라고 하셨다. 구조는 `page → LoginForm → FormField → Input`. 페이지가 데이터 통신(서버 액션)을 담당하고, 폼 안의 입력 값 관리는 컴포넌트가 한다. 자식이 부모한테 값을 못 올려주는 건 form 안의 input을 name으로 꺼내면 해결된다.

## useState는 한 박자 늦는다

버튼 활성화 조건을 만들다가 겪은 일이다. `setPayload`로 값을 바꾼 직후에 `payload`를 읽어서 검사하면 이전 값이 나온다. 상태 변경은 리렌더링이 돼야 반영되는데, 그 함수가 끝나기 전에는 아직 이전 값을 보고 있기 때문이다. 그래서 A를 입력했는데 버튼이 활성화 안 되고 한 글자 더 쳐야 반응한다.

해결은 `payload`가 아니라 지금 입력 중인 `e.target.value`로 검사하는 것. 코드가 틀린 게 아니다.. 

핸들러 하나로 여러 input을 관리하는 패턴도 같이 배웠다.

```tsx
const handleChange = (e) => {
  const { name, value } = e.target
  setPayload((prev) => ({ ...prev, [name]: value }))
}
```

에러 메시지는 `ErrorMessage` atom을 따로 만들었다. 에러 없을 때 자리를 차지하게 할지 말지는 디자인 문제인데, 안 잡아두면 에러가 뜰 때 화면이 덜컹거린다. 서서히 나타나게 하려면 `hidden` 대신 `opacity`와 `transition`을 쓴다.

## Zod로 검증 분리

조건문이 점점 길어져서 Zod를 도입했다. 상태를 따로 안 두고도 입력할 때마다 검증 결과를 알 수 있다.

```ts
export const loginSchema = z.object({
  userId: z.string().min(1, '아이디를 입력해 주세요'),
  password: z.string().min(1, '비밀번호를 입력해 주세요'),
})

const isValid = loginSchema.safeParse(payload).success
```

- 로그인은 "글자 하나만 있으면 OK" 정도가 일반적이다. 글자 수 같은 검증은 회원가입에서 복잡해진다
- 중간에 `disabled`와 `valid`가 반대 개념인 걸 헷갈려서 한 번 고쳤다. 강사님도 AI랑 생각이 반대로 갈 때가 있다고
- 스키마는 `schemas/`, 타입은 `types/`로 빼두면 컴포넌트를 열어보지 않아도 타입을 볼 수 있어서 관리가 편하다
- 라이브러리는 유행이 바뀔 수 있으니 의존만 하지 말고, 직접 구현할 수 있으면 더 좋다고 하셨다

`useMemo`가 필요하냐고 AI에게 물어봤는데, Zod를 쓰고 있어서 `handleChange`에는 필요 없다고 했다. 상태는 최소화할수록 좋다는 말도 반복하셨다.

## FormField와 UX 개선

`Input`과 에러 메시지를 묶어서 `FormField`로 만들었다. div로 감쌌더니 hydration 에러가 나서 fragment로 바꿨다.

AI한테 시켜서 이런 기능도 붙였다. "AI를 잘 다루는 건 결국 뭘 요구할지 아는 것"이라고 하셨다. 나도 체감한다.

- 값이 있으면 X 버튼이 떠서 한 번에 지우기. `isClearable` 같은 옵션 prop으로 필요할 때만 쓰게 만들면 더 좋은 컴포넌트가 된다
- 비밀번호 보기/숨기기 토글. input의 `type`을 `password`와 `text`로 바꾸는 게 전부다. 아이콘은 lucide-react

아이콘을 input 안쪽에 붙일 때는 CSS가 필요했다. 부모에 `relative`, 아이콘에 `absolute`를 주고, 세로 가운데는 `top: 50%`로 내린 다음 `-translate-y-1/2`로 절반을 다시 올린다. `top: 50%`만 하면 요소의 위쪽 꼭짓점이 중앙에 오기 때문이다. 퍼블리셔도 AI도 없는 상황을 대비해서 원리는 알아두라고 하셨다.

### 서버/클라이언트 컴포넌트 규칙

- 아무것도 안 쓰면 서버 컴포넌트가 기본이다
- 클릭이나 체인지 같은 유저 행동 감지가 들어가면 `'use client'`가 필요하고, 그 아래 자식은 전부 클라이언트 렌더링에 종속된다. 그래서 구조 설계를 잘해야 클라이언트 영역을 최소화할 수 있다
- 클라이언트 쪽으로 내려오는 props는 확정이 아니다. 안 들어올 수도 있으니 `onClear && ...`처럼 존재 확인이 필요하다. 이걸 빼면 개발 모드에선 되다가 배포 빌드에서 터질 수 있다
- hydration error는 서버와 클라이언트가 그린 결과가 다를 때 나는 Next의 고질병이다. 리액트는 warning으로 넘어가는 걸 Next는 error로 띄운다. 무시하고 가면 나중에 다 문제가 된다

로그인 버튼 정책도 얘기가 나왔다. 빈 값이면 버튼을 비활성화할지, 클릭을 허용하고 에러 메시지로 안내할지는 기획팀이랑 정해야 한다. 네이버는 후자.

## 백엔드 API 연동 시작

강사님이 Docker로 띄워둔 Spring 서버(8080)에 붙었다. 스웨거에서 가입, 로그인을 해보니 JWT가 발급됐다.

Docker는 개발 환경을 통일하려고 쓰는 가상 환경(컨테이너)이다. 내 컴퓨터에선 되는데 남이 받으면 안 되는 상황(Node 버전, 리눅스 버전 등)을 없애려는 목적이다. 윈도우는 설치할 때 WSL2가 필요하다. Docker Hub에서는 공식(Official) 이미지만 받아야 한다. 이상한 이미지를 받으면 엉뚱한 게 설치될 수 있다.

### fetch 코드에서 배운 것

```ts
const res = await fetch(LOGIN_API_URL, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ email, password }),
})
```

- 처음에 에러가 났는데 `Content-Type` 헤더를 빠뜨려서였다. 네트워크 탭의 Headers, Payload, Response를 보면서 확인하는 습관이 필요하다
- 서버 주소는 `.env`로 빼고, 서버 주소(BASE_URL)와 API 경로를 따로 둔다. 배포 환경마다 앞부분이 바뀌고, 경로는 v2로 바뀔 수 있어서다
- 서버에서 응답을 받으면 브라우저 네트워크 탭에 안 보이고, 쿠키나 세션에도 아무것도 안 남는다. 서버가 받은 걸 다시 클라이언트로 내려줘야 브라우저가 로그인 여부를 안다. 그래서 로그인에 성공해도 화면은 그대로다. 전부 손으로 해줘야 한다

### 버튼 연타 방지

로그인 버튼을 7번 누르니까 서버에 7번 다 요청이 갔다. `useFormStatus`의 `pending`을 쓰면 폼 안의 버튼이 요청 진행 중인지 알 수 있어서 "로그인 중…"으로 바꾸고 막을 수 있다. 예전엔 쓰로틀링 같은 걸 직접 써야 했다고 한다. 폼을 쓰는 것만으로 이런 장점이 따라온다.

`pending`은 진행 중인지만 알고 결과는 모른다. 성공/실패 처리는 서버 액션 안에서 한다. 서버 액션에서는 `redirect`, 클라이언트에서는 `useRouter`를 쓴다.

## HTTP는 stateless

서버는 이전 요청을 기억하지 않는다. 그래서 로그인 상태를 유지하려면 쿠키, 세션, 토큰 중 하나가 필요하다. 면접 단골 질문이라고 한다.

- 4xx는 클라이언트 쪽 문제, 5xx는 서버 쪽 문제. 401(인증 필요), 403(권한 없음), 404는 알아두기
- 스웨거에서 자물쇠가 있는 API는 로그인(토큰)이 필요한 API다. 로그인 후 받은 access token을 Authorize에 넣으면 `Authorization: Bearer 토큰`이 헤더에 붙는다

### 토큰을 어디에 둘 것인가

브라우저 메모리나 로컬스토리지에 두면 노출된다. 이건 해킹도 아니고 개발자가 아닌 사람도 AI한테 물어보면 할 수 있다고 한다. 실제로 비전공자가 AI로 해킹 툴을 만들어서 노출된 API를 찾아 개인정보를 털어간 사례가 있다고 한다...무서운 세상

그래서 강사님의 방향은 통신은 Next 서버가 대신하고, 로그인 이후 값은 서버에서 세션으로 관리해서 쿠키로 브라우저에 내려주는 것이다.

1. 브라우저 → Next 서버 (로그인 요청)
2. Next 서버 → API 서버
3. 응답으로 받은 토큰으로 쿠키를 만들어 브라우저에 내려줌
4. 이후 요청마다 쿠키가 자동으로 같이 감
5. 서버 액션에서 쿠키를 열어 토큰을 꺼내 API를 호출

`cookies()`로 쿠키를 만들고 개발자 도구 Application → Cookies에서 확인했다.

### Context API → 한계 → 미들웨어

로그인 여부를 `AuthProvider`(Context API)로 전역에 공유해봤는데 한계가 많았다.

- `useAuth` 같은 훅은 서버 컴포넌트에서 못 쓴다
- 로그인 페이지가 먼저 렌더링되고 나서 상태를 확인해 튕겨내니까 UX가 안 좋다
- hydration error가 계속 터졌다
- 리다이렉트는 `router.push`가 아니라 `router.replace`를 써야 뒤로 가기에서 무한 반복이 안 생긴다

그래서 목표는 미들웨어(지금은 이름이 `proxy`로 바뀜)다. 페이지가 렌더링되기 전에 서버에서 세션을 확인해서 막는 방식이다.

## 로그아웃은 서버도 처리해야 한다

강사님이 "로그아웃은 클라이언트만 하면 될까요?"라고 물어보셨다. 프론트는 보통 상태만 지우고 끝내는데, 백엔드는 로그아웃 요청을 받아야 한다. JWT는 서버가 발급한 뒤에는 만료 전까지 강제로 지울 수 없기 때문이다.

출입증 비유가 이해하기 쉬웠다. 3개월짜리 출입증을 잃어버렸는데 누가 주워서 쓸 수 있다면, 관리자한테 신고해야 막을 수 있다. 그런데 어떤 키를 누구한테 발급했는지 기록이 없으면 못 막는다. 그래서 발급할 때마다 발급 대장에 적어두는데, 이걸 보통 Redis로 한다. 메모리 기반이라 빠르고, key-value 형태고, 만료 시간이 지나면 자동으로 삭제되는 기능(TTL)이 있다. 로그아웃이 오면 대장에서 지운다.

## DB 연결: MongoDB Atlas, Compass

서버 연동이 막혀서(HTTPS 인증서 문제, 학생용 계정이 없는 문제) 방향을 바꿔서, Next에서 직접 DB에 붙는 방식으로 갔다.

- MongoDB Atlas에 가입해서 무료 클러스터를 만든다. 무료는 1개만 가능하고, 클러스터는 노드 3개(레플리카셋)로 구성된다
- Connect → Compass로 연결 문자열을 복사해서 `<password>` 자리를 내 DB 비밀번호로 바꾼다. 연결된 상태에서는 문자열 복사가 안 되니까 연결을 끊고 Edit Connection String에서 본다
- Compass에서 Create Database(DB 이름 + 컬렉션 이름)를 만들고, `Add Data → Insert Document`로 샘플 데이터를 넣는다. 몽고의 Document는 JSON 형태고 키에 큰따옴표가 꼭 필요하다
- 샘플 계정의 password는 해시된 값이어야 로그인이 된다. 
- 연결이 안 되면 Atlas의 Network Access(IP 허용)와 Database Access(유저)를 확인한다

몽고DB가 NoSQL이라 스키마가 없어서, 나중에 필드를 추가해도 기존 데이터에 영향이 없다. 채팅 같은 데이터에 많이 쓴다. 이번 프로젝트의 채팅 때문에 미리 한 거였다.

MySQL을 로컬에 설치할 때 주의할 점도 들었다. root 비밀번호를 잃어버리면 컴퓨터를 포맷해야 할 수도 있다고 한다. 유료 라이선스가 싫으면 MariaDB를 쓰면 되고, 명령어는 거의 같다.

## Next API Route와 Prisma

- `app/api/.../route.ts`를 만들면 API 주소가 생긴다. `GET`, `POST` 함수를 export해서 만든다
- 요청 흐름은 `화면 → fetch → route.ts → service → Prisma → MongoDB`다. 로그인 페이지에서 서비스를 바로 부르는 게 아니라 API를 거쳐야 책임 분리가 된다
- Prisma는 ORM이다. 몽고 쿼리를 직접 쓰는 대신 `prisma.user.findUnique(...)`, `prisma.user.create(...)` 같은 객체 코드로 쓴다. 백엔드의 JPA 같은 것이고, `schema.prisma`에 스키마를 정의한다
- 비밀번호는 해시해서 저장한다. 토큰 발행은 아직 구현 전이고 내일 이어서 한다
- Prisma + Zod + Next API 조합이 프론트 기술을 거의 최대로 쓰는 풀스택 구성이라고 하셨다

### .env 사고

DB 주소 같은 건 `.env`에 둔다. Next가 실행될 때 `.env`를 가장 먼저 읽고, 그 다음 `.env.local` 순으로 읽는다. 절대 깃에 올리면 안 된다.
