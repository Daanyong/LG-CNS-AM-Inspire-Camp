## 1. 무한 스크롤 구현
* 기존에 구현했던 페이지네이션을 무한 스크롤로 변경했다. 평소에는 무한 스크롤이란 생각도 안 하던 것들이 생각보다 복잡하고 프론트엔드 입장에서는 챙길 게 꽤 많았다.

* 어떻게 구현할까
리스트 최하단에 div로 빈 박스를 하나 두고, `useRef`와 `IntersectionObserver`를 사용해서 이 박스가 화면에 나타나는지 감시한다. 박스가 화면에 보이면 다음 페이지 데이터를 API로 요청하는 방식이다.

* Next.js 렌더링 방식
무한 스크롤 시 라우팅이 변경되면 스크롤이 맨 위로 튀어 올라가는 문제가 있어서 `router.push` 옵션에 `scroll: false`를 줘서 위치를 고정했다. 브라우저 뒤로가기 시 히스토리가 엄청 쌓이는 걸 막으려고 `router.replace`를 활용하는 디테일도 추가했다.
Next.js는 페이지 번호가 바뀌어도 리렌더링을 처음부터 하지 않고, 기존에 그려진 데이터 아래에 새로운 데이터를 합쳐서 렌더링한다. ssr과 csr이 섞여서 동작하는 걸 잘 활용해보고 싶었따.

* 강사님 조언
무한 스크롤 해달라고 하면 기획자랑 심도 있게 상의하라고 하셨다.ㅋㅋㅋ 새로고침 했을 때 5페이지 중간이면 데이터를 어디서부터 부를 건지, 오래된 순 정렬을 누르면 데이터를 싹 갈아엎을 건지 등 조건이 많아질수록 코드가 복잡해진다. 멋있어 보인다고 남발하지 말자!!!!

## 2. 프론트엔드 아키텍처와 SOLID 원칙
무한 스크롤 코드를 짜다 보니 상태 관리가 꼬이면서 코드가 급격히 복잡해졌다. 강사님이 이럴 때일수록 원칙으로 돌아가야 한다며 로버트 C. 마틴의 SOLID 원칙을 강조하셨다.

- 단일 책임 원칙 (SRP): 하나의 함수는 하나의 일만 해야 한다. 연산하는 로직과 화면 그리는 로직을 섞지 말 것.
- 개방-폐쇄 원칙 (OCP): 확장에 열려 있고 수정엔 닫혀 있어야 한다.
- 액션과 계산의 분리: 프론트엔드는 데이터를 받아 화면에 뿌리는 역할이 크니까 Action과 Service를 철저히 분리해야 나중에 API가 바뀌어도 코드가 덜 꼬인다.

프론트엔드도 최소한 S, O, I 원칙은 지켜야 좋은 소프트웨어가 나온다고 하셨다. AI가 코드를 짜주는 시대일수록 구조 설계에 더 시간을 많이 써야겠다고 생각했다.

## 3. API 마이그레이션 (어댑터 패턴)
기존에는 Next.js 안에서 Prisma로 DB에 다이렉트로 붙었다면, 이제는 Spring API 서버와 통신하는 구조로 마이그레이션했다.

Custom Fetch Client 도입
강사님이 실무에서 쓰시던 Fetch Client 유틸을 받아서 적용했다. API 주소들은 하드코딩하지 않고 config 폴더에 `api_uri.ts`로 빼서 키-밸류 형태로 관리한다. 이렇게 하면 나중에 버전이 바뀌어도 한 곳만 수정하면 돼서 편하다고 하셨다.

NextAuth와 백엔드 통신
기존 `credentials` 방식의 로그인 로직을 Spring API를 호출하는 방식으로 변경했다. Spring에서 발급한 `AccessToken`을 NextAuth의 Session 객체에 담아서 전역에서 사용한다. 민감 정보는 애초에 백엔드에서 프론트로 안 내려주는 게 맞고, 토큰 유효성만 검증하고 정보는 마스킹 처리해야 한다는 보안 팁도 얻었다.
