## 1. 자바 에디션

### 스탠다드 에디션
- 어제 설치한 JDK가 이거다. 서버 없이 로컬에서 단독으로 실행되는 자바 애플리케이션(stand alone)을 만들 때 쓴다
- 파일 입출력(`java.io`), 네트워크(`java.net`), 보안(`java.security`), DB 연동(`java.sql`, JDBC), 날짜(`java.time`), 컬렉션 같은 `java.util` 등이 여기 들어 있다
- 자바 9부터는 패키지가 너무 많아서 모듈로 묶었다. 자주 쓰는 `io`, `lang`, `util` 등은 `java.base` 모듈에 있어서 따로 신경 안 써도 되고, `java.sql` 같은 건 별도 모듈이라 쓰려면 모듈을 언급해줘야 한다

### 엔터프라이즈 에디션
- 기업 업무용 애플리케이션을 만들 때 필요한 기술 모음. 서블릿, JSP, JPA, 트랜잭션, 밸리데이션 같은 것들이 있고 스프링 프레임워크와 스프링 부트의 베이스가 된다
- 톰캣 같은 서버(웹 컨테이너)가 필요하다
- 원래 오라클이 관리했는데 이클립스 재단으로 넘어가면서 이름이 자카르타 EE로 바뀌었고 패키지명도 `javax`에서 `jakarta`로 바뀌었다. 스프링 부트 2까지는 `javax`, 3부터는 `jakarta` 기반이다. 패키지명이 바뀌면 기존 코드를 다 고치고 다시 컴파일, 테스트해야 해서 현업에서는 꽤 큰 혼란이었다고 한다

### 인터페이스만 있고 구현은 벤더가 한다
- 자카르타 EE API 문서를 보면 거의 다 인터페이스다. 즉 표준 스펙만 정해놓은 거고 구현은 서버 만드는 업체들이 한다
- 웹 서버(nginx, 아파치)는 정적인 HTML, CSS, JS를 처리하고, 자바 웹 애플리케이션은 JVM이 필요하니까 JVM을 내장한 웹 컨테이너(톰캣)를 쓴다. 웹 컨테이너에 EJB 컨테이너 같은 기능까지 합친 게 WAS이고 제이보스, 웹스피어, 웹로직, 제우스 등이 있다
- 스프링은 비싼 WAS 없이 톰캣 같은 간단한 컨테이너만 있어도 자카르타 EE의 기술들이 동작하게 만든 프레임워크다

## 2. Account 실습 (캡슐화)

### 구현한 것
- `Account` 엔티티: 고객번호, 계좌번호, 잔액을 전부 private으로 선언하고 getter, setter를 만들었다
- `setBalance`는 만들지 않고 대신 `deposit`(입금), `withdraw`(출금) 메서드를 만들었다
- `AccountTest`: 기본 생성자 + setter로 객체를 만든 경우와 인자 있는 생성자로 만든 경우를 둘 다 해보고 값을 출력했다

### 개념 정리
- 캡슐화는 변수를 private으로 막고 getter, setter로만 접근하게 해서 잘못된 값이 들어오는 걸 막는 것. 잔액을 setter로 마음대로 바꾸게 두지 않고 입금, 출금 메서드로만 바꾸게 한 것도 같은 이유
- getter, setter는 직접 치기, 이름 일부 치고 `Ctrl + Space`, Source 메뉴의 Generate로 한꺼번에 만들기 세 가지 방법이 있다. 롬복을 쓰면 `@Getter`, `@Setter`로 끝나는데 스프링 부트 때 쓴다
- 생성자를 하나라도 직접 만들면 컴파일러가 기본 생성자를 자동으로 안 만들어준다. 그래서 인자 있는 생성자를 만들면 기본 생성자도 직접 추가해야 한다

## 3. toString과 오버라이딩

### 개념 정리
- 모든 클래스는 `extends Object`가 생략된 채로 `Object`의 자식이다
- `Object`의 `toString()`은 클래스 이름 + `@` + 해시코드를 돌려준다. 그래서 `System.out.println(account)`처럼 객체를 바로 넣으면 `println`이 `toString`을 자동으로 호출해서 이상한 값이 나온다
- 부모가 물려준 메서드가 내 쓰임새랑 안 맞으면 자식에서 오버라이딩한다. `toString`을 오버라이딩해서 고객번호, 계좌번호, 잔액이 출력되게 했다 (Source 메뉴에서 자동 생성 가능)
- 오버라이딩 규칙: 접근제한자, 리턴 타입, 메서드 이름, 인자가 부모랑 같아야 한다
- 추상 메서드는 자식이 반드시 오버라이딩해야 하고, 이미 구현된 메서드는 부모 동작이 내 동작이랑 같으면 그냥 쓰고 다르면 오버라이딩한다. 수업 예시는 동물 그림이었는데 `eat`은 추상이라 다 오버라이딩하고, `walk`는 걷는 동물은 그대로 쓰고 물고기만 오버라이딩했다

### `@Override`
- 메서드 이름 오타 같은 걸 컴파일 타임에 잡아주는 어노테이션이다. 없으면 오타 낸 메서드가 그냥 새 메서드가 돼서 에러 없이 넘어가고, 실행해보고 나서야 부모 `toString`이 호출되는 걸 발견하게 된다
- 어노테이션 안을 보면 `@Target`(어디에 붙일 수 있는지)과 `@Retention`(언제까지 유지되는지)이 있다. `@Override`는 메서드에만 붙고 컴파일러가 체크하는 용도이고, 스프링 어노테이션은 대부분 실행 시점에 동작한다
- JPA 엔티티에서는 `toString`에 연관된 다른 엔티티가 같이 찍히면서 쿼리가 나갈 수 있어서 조심해야 한다고 하셨다

## 4. 사용자 정의 예외

### 구현한 것
- `InsufficientBalanceException`: `Exception`을 상속받고 `currentBalance` 필드와 getter를 가진다. 생성자에서 `super(message)`로 부모에게 메시지를 넘긴다
- `Account.withdraw`: 출금액이 잔액보다 크면 이 예외를 만들어서 `throw`하고, 메서드 선언부에 `throws`를 붙였다
- `AccountTest`: 출금하는 부분을 `try-catch`로 감싸서 예외 메시지와 현재 잔액을 출력했다. 두 번째 출금(6만 원)에서 예외가 터지면 그 아래 출력문은 실행되지 않고 바로 catch로 넘어갔다

### 개념 정리
- 자바에 있는 예외 클래스 중에 상황에 딱 맞는 게 없으면 `Exception`을 상속받아서 직접 만든다. 구조는 `Object` → `Throwable` → `Exception` → 내가 만든 예외
- `Throwable`에서 물려받는 것: `getMessage()`, `getStackTrace()`, `printStackTrace()`. stack trace는 메서드 호출 순서가 쌓인 정보인데 운영자가 로그로 봐야 하는 거고 외부에 노출하면 구조가 드러나서 보안에 안 좋다
- `throw`는 예외를 실제로 발생시키는 것이고 `throws`는 메서드 선언부에서 이 예외를 호출한 쪽으로 넘기겠다고 선언하는 것. 둘이 세트로 많이 쓰인다
- 예외를 발생시켰으면 그 자리에서 `try-catch`로 처리하거나 `throws`로 넘겨야 한다. 안 그러면 `Unhandled exception` 에러가 난다
- 역할 분담: 던지는 쪽(`Account`)은 문제가 생겼다고만 알리고, 호출하는 쪽(`AccountTest`)이 어떻게 처리할지 정한다

## 5. 배열

### 개념 정리
- 변수 타입은 기본형 8가지(`byte`, `short`, `int`, `long`, `float`, `double`, `char`, `boolean`)와 그 외 전부 참조형으로 나뉜다. `String`도 참조형이다. 기본형 기본값은 정수 `int`, 실수 `double`이고, 기본형마다 래퍼 클래스가 있어서 `int`와 `Integer`를 자동으로 오갈 수 있다 (오토박싱, 언박싱)
- 배열은 같은 타입 값을 하나의 이름으로 묶는 것이고 배열 자체는 참조형이다. `new`로 만들면 힙에 생기고 스택의 변수에는 그 주소가 들어간다. 선언은 `int[] a`처럼 타입 옆에 `[]`를 붙이는 걸 권장하신다
- 인덱스는 0부터 `length - 1`까지이고 범위를 벗어나면 `ArrayIndexOutOfBoundsException`
- 기본형 배열은 `new`하면 0으로 초기화된 값이 방에 바로 들어가고, 참조형 배열은 방이 전부 `null`이다. 각 방에 `new`로 객체를 만들어 넣으면 방에는 객체가 아니라 그 객체의 주소가 들어간다
- 반복문은 기존 for문도 되지만 향상된 for문을 권장한다. 나중에 배열을 컬렉션으로 바꿔도 반복문 코드를 안 고쳐도 되기 때문
- 배열의 한계: 크기를 고정해서 선언해야 해서 DB에서 몇 건이 올지 모르는 상황에는 맞지 않는다. 그래서 컬렉션을 쓴다

## 6. static과 non-static

### 개념 정리
- `main`(static)에서 non-static 메서드를 바로 호출하면 에러가 나는 이유: static은 클래스가 로딩될 때 메모리에 올라가는데, non-static은 `new`로 객체를 만들 때 힙에 생긴다. static이 실행되는 시점에는 non-static이 아직 없을 수 있다. 또 non-static은 `this`가 있는데 static은 특정 객체 소속이 아니라서 `this`가 없다. 그래서 객체를 먼저 만들고 그 참조 변수로 호출해야 한다
- 그럼 전부 static으로 하면 안 되냐고 하면, 객체마다 다른 상태 값(이름, 장바구니 등)을 가질 수 없고 상속, 오버라이딩, 다형성도 못 쓰게 돼서 객체지향의 장점을 포기하는 거라고 한다
- 정리하면 static은 `Math.abs()`처럼 상태와 무관하게 항상 같은 결과를 내는 유틸 메서드나 모든 객체가 공유하는 값에 쓰고, 객체마다 달라야 하는 속성은 non-static으로 둔다

## 7. PersonEntity, PersonManager 실습

### 구현한 것
- `PersonEntity`: 이름, 성별, 주민번호, 주소, 전화번호 필드. 인자 있는 생성자는 성별을 뺀 4개만 받는다. `setSsn`에서 주민번호 7번째 자리(`charAt(6)`)가 1, 3이면 남, 아니면 여로 성별을 자동 세팅한다
- `PersonManager`: `PersonEntity` 10개짜리 배열을 만들고 메서드 4개를 구현했다
  - `fillPersons`: 배열에 10명 정보를 채움
  - `showPersons`: 향상된 for문으로 전체 목록 출력
  - `findByGender`: 입력받은 성별과 같은 사람 수를 세서 리턴
  - `showPerson`: 이름으로 찾아서 상세 정보를 출력하고 `break`

### 개념 정리
- 생성자에서 `this.ssn = ssn`처럼 직접 대입하지 않고 `setSsn(ssn)`을 호출하는 이유는, setter 안에 있는 로직(성별 계산, 값 검증)이 생성자로 객체를 만들 때도 똑같이 적용되게 하려는 것. 어제 `MyDate`의 월 범위 검증이랑 같은 맥락이다
- `char` 같은 기본형은 `==`로 값 비교가 되지만, `String`은 참조형이라 `==`는 주소 비교가 돼서 `equals`로 내용을 비교해야 한다. 화면 코드에는 `contentEquals`를 썼는데 이것도 문자열 내용 비교라서 결과는 같지만 수업에서 설명한 건 `equals`다
- main에서 non-static 메서드를 쓰려고 `PersonManager` 객체를 먼저 생성했다 (6번 내용 적용)
- 한 줄 팁: 에디터의 컬럼 셀렉션(`Alt + Shift + A`)을 쓰면 여러 줄 앞에 `private`을 한 번에 칠 수 있다

## 8. 컬렉션과 제네릭

### 컬렉션
- 객체를 여러 개 담는 컨테이너이고 `java.util`에 있다. 저장할 때마다 크기가 자동으로 늘어나서 배열의 크기 고정 문제를 해결한다
- 리스트 계열: 순서 유지, 중복 허용. `ArrayList`(가장 많이 씀), `Vector`(오래됨, 느림), `LinkedList`(중간 삽입, 삭제에 유리)
- 셋 계열: 순서 없음, 중복 불가. `HashSet`, `TreeSet`. 해시코드와 `equals`로 같은 객체인지 판단한다
- 맵 계열: 키와 값을 쌍으로 저장하고 키는 중복 불가. `HashMap`을 주로 쓰고 `Hashtable`은 옛날 것

### 제네릭
- 타입을 안 정하고 `List list = new ArrayList();`로 쓰면 아무 타입이나 들어가고, 꺼낼 때 다 `Object`로 나와서 형변환하다가 실행 중에 에러가 날 수 있었다
- 그래서 `List<String>`처럼 담을 타입을 꺾쇠로 정해두면 다른 타입을 넣을 때 컴파일 에러가 나서 미리 막을 수 있다. 오른쪽은 `<>`로 비워도 된다
- 왼쪽을 `List`로 쓰는 것과 `ArrayList`로 쓰는 것의 차이는 다형성이랑 연결된다고 하셨고 내일 설명해주신다. 일단 `List`로 쓰면 호출할 수 있는 메서드는 좁아지지만 나중에 `LinkedList`로 바꿔도 코드를 안 고쳐도 되는 유연함이 있다고만 이해했다
