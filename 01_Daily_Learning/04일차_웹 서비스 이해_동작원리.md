## 💡 공부한 내용 본인의 언어로 정리하기

### 1. HTTP vs HTTPS 프로토콜의 이해
웹에서 클라이언트와 서버가 데이터를 주고받기 위해 사용하는 통신 규약이다.

- **HTTP (HyperText Transfer Protocol)**
  - 데이터를 암호화하지 않고 평문으로 전송함
  - 도청 및 변조 위험이 있어 보안이 중요하지 않은 단순 테스트/내부망 서비스에서 제한적으로 사용
- **HTTPS (HyperText Transfer Protocol Secure)**
  - HTTP에 **SSL/TLS 암호화 프로토콜**을 추가하여 보안성을 강화한 방식
  - 모든 데이터를 암호화하여 전송하며, 브라우저 주소창에 자물쇠 아이콘으로 표시됨
  - 로그인, 결제, 쇼핑몰 등 민감한 개인정보를 다루는 현대 서비스의 필수 표준

---

### 2. HTTP 요청(Request)과 RESTful URL 설계 규칙

#### 1) 주요 HTTP Method (행위의 정의)
- **GET**: 데이터 조회 (`GET /users/1`)
- **POST**: 새로운 데이터 생성 (`POST /users`)
- **PUT**: 데이터 전체 수정/교체 (`PUT /users/1`)
- **PATCH**: 데이터 일부 수정 (`PATCH /users/1`)
- **DELETE**: 데이터 삭제 (`DELETE /users/1`)

#### 2) RESTful URL 설계 핵심 원칙
- **리소스(Resource)는 명사형**으로 표현한다. (예: `/users` ⭕, `/getUser` ❌)
- **계층적 구조**를 반영한다. (예: `/users/{userId}/posts/{postId}`)
- 행위(동작)는 URL에 담지 않고 **HTTP Method로 구분**한다.

#### 3) Header & Body
- **Headers**: 메타데이터 전달 (예: `Content-Type: application/json`, `Authorization: Bearer <JWT>`)
- **Request Body**: POST, PUT, PATCH 요청 시 실제로 전달할 JSON 데이터를 담는 본문 영역

---

### 3. HTTP 응답(Response)과 상태 코드 (Status Code)

서버가 클라이언트 요청을 처리한 후의 상태 결과를 숫자 코드로 반환한다.

- **2xx (Success - 성공)**
  - `200 OK`: 요청이 정상 처리됨
  - `201 Created`: 새로운 리소스 생성 완료
  - `204 No Content`: 요청은 성공했으나 반환할 본문 데이터가 없음
- **4xx (Client Error - 클라이언트 오류)**
  - `400 Bad Request`: 잘못된 문법이나 파라미터 전달 등으로 인한 요청 오류
  - `401 Unauthorized`: 인증 실패 (로그인 필요)
  - `403 Forbidden`: 권한 부족으로 접근 거부
  - `404 Not Found`: 요청한 리소스가 존재하지 않음
- **5xx (Server Error - 서버 오류)**
  - `500 Internal Server Error`: 서버 내부 로직 장애 발생

### 4. API 명세서 작성 표준 구조 (API Specification)
프론트엔드와 백엔드가 차질 없이 소통하기 위해 API 구조를 문서화한다.

| 항목 | 내용 예시 |
| :--- | :--- |
| **URL (Endpoint)** | `/users/{id}` |
| **Method** | `GET` |
| **설명** | 특정 사용자 정보 조회 |
| **Request Header** | `Authorization: Bearer {token}` |
| **Path Variable** | `id (Long, 정수)` |
| **Response 200** | `{"id": 1, "username": "testuser", "email": "test@example.com"}` |
| **Response 404** | `{"status": "error", "message": "User not found"}` |

REST API의 핵심 철학인 'URL에는 자원(명사)만 명시하고, 행위(동사)는 HTTP Method로 표현한다'는 원칙을 제대로 정립할 수 있었다. HTTP 상태 코드(200, 201, 401, 404 등)의 세부적인 의미와 응답 헤더/바디의 정확한 역할을 확실하게 정리하여 이후 개발에서 큰 도움이 될 듯하다.
